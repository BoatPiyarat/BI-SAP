## Required Note — "row conservation" is a count match across two unlinked identifiers, not a set match

`v_identity_rows` (line 40–45) is scoped entirely by `p_pipeline_run_id` (via
`v3_unit5_payload_identity.pipeline_run_id` and `v3_unit5_balance_hold.pipeline_run_id`).
`v_archive_rows` and every other check in this procedure (lines 46–89) is scoped entirely by
`p_export_run_id`. Checked `export_archive`'s live schema directly: **it has no `pipeline_run_id`
column at all** — there is no structural link between the two identifiers anywhere in this
procedure. The conservation check at line 51 (`v_archive_rows=v_identity_rows`) only proves the
*counts* match; it does not prove the archived rows are the *same identities* the claimed pipeline
run actually produced.

Both tables already carry everything needed for a real identity-level check —
`v3_unit5_payload_identity` and `export_archive` both have `order_item`, `period`, `charge_id`,
and `payload_hash` — so a `NOT EXISTS` anti-join or exact `payload_hash` comparison is directly
buildable with existing columns, matching the exact pattern this project's own prior review
required for a structurally similar gap (`docs/reviews/2026-08-04-913ff3b-claude.md`, Unit 6
natural-key/`payload_hash` binding).

Concretely: if a caller ever supplied a `p_pipeline_run_id` that doesn't actually correspond to
the `p_export_run_id` being marked delivered — e.g. a stale value reused across a retry, or any
copy-paste mismatch in the calling code — and the two run's identity counts happened to be equal,
this procedure would silently accept it as fully conserved. This requires an internal caller
mistake to trigger, not external input, and every other named check (filename-exactness, replay
protection on three vectors, atomicity) is sound — so I'm not blocking the whole artifact on it,
but "row conservation" as stated in the review request implies more than count equality, and the
fix is a straightforward join using columns that already exist on both sides.

**Fix required before deploy:** replace or supplement the count comparison with a set-level check
— e.g. assert zero rows exist in `v3_unit5_payload_identity` (for `p_pipeline_run_id`, minus
balance-held items) that don't have a matching `export_archive` row for `p_export_run_id` on
`(order_item, period, charge_id)` or `payload_hash`, and vice versa.

## Non-blocking observation

The replay-guard `ASSERT`s (lines 56–63) run *before* `BEGIN TRANSACTION` (line 65), so they carry
no isolation guarantee against a second concurrent call for the same `export_run_id`/
`production_uri`/`sap_file_name` — BigQuery has no unique constraints (documented project-wide,
e.g. `sql/ddl/064_sap_result_ingestion_contract.sql`'s own header). Given this procedure is called
once per gated production promotion by a single deployer per this project's standing operational
discipline, concurrent double-invocation is operationally unlikely, so I'm not requiring a fix —
flagging as forward-looking, same category as the non-blocking notes already accepted in
`docs/reviews/2026-08-04-913ff3b-claude.md`.

## Verdict

PASS WITH REQUIRED NOTE. Filename-exactness, atomicity, and all three replay-protection vectors are
correctly implemented and independently verified. The conservation check needs to move from a bare
count comparison to a set/identity-level check before deploy — the columns needed already exist on
both source tables. No deployment, procedure CALL, GCS write, Gmail, scheduler, BigQuery table
mutation, or SAP action is requested or occurred in this review.

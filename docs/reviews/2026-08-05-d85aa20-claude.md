## What changed

`dispatchPendingV3DailyCompletenessReports` now wraps each per-run
`deliverV3DailyCompletenessReport_` call in its own try/catch inside the `forEach`, pushing
`${pipelineRunId}:${completenessSanitize_(error)}` onto a `failures` array instead of letting the
exception propagate. After the loop finishes, `if (failures.length)` raises one aggregated,
sanitized `Error` listing every failed run.

## Verification

- **Each pending report is attempted independently**: confirmed — the try/catch is inside the
  `forEach` callback itself, so an exception from one iteration is caught before the callback
  returns; the `forEach` has no way to know an error occurred and proceeds to the next row
  regardless. Traced this is the correct fix for exactly the mechanism I flagged in the base
  review (a throw inside a `forEach` callback aborts the whole loop when uncaught).
- **A failure in one run cannot stop later pending runs**: direct consequence of the above — since
  the loop itself never sees an exception, no run after a failing one is skipped.
- **Sanitized aggregate raised only after the batch completes**: `failures.push(...)` happens
  inside the loop; the `if (failures.length) throw ...` is the last statement in the function,
  strictly after `forEach` has returned. Reuses the existing `completenessSanitize_` helper rather
  than introducing new redaction logic — applying it to an already-sanitized inner error message
  (see below) is idempotent (email-redaction and the 300-char truncation both no-op on
  already-processed input), so no information is doubly mangled, just harmlessly re-passed through
  the same filter.
- **Existing per-run `ALERT_FAILED`-then-fallback behavior remains intact**: read the complete
  current file end-to-end, not just the diff — `deliverV3DailyCompletenessReport_` is byte-for-byte
  unchanged from the base commit. `ALERT_FAILED` is still persisted before the fallback attempt,
  the distinct-recipient enforcement in `completenessConfig_` is untouched, and the function still
  throws even when the fallback succeeds (by design, so the primary-channel failure is never
  silently absorbed) — that throw is exactly what the new outer try/catch now correctly isolates
  per-run instead of letting it abort the whole batch.
- **No new failure mode introduced**: if *every* pending run fails, `failures.length` is still
  truthy and the aggregate throw still fires, so Apps Script's own exception logging still sees a
  failure — the fix doesn't accidentally make total failure look silent.

Independently re-verified with `node --check` (renamed to `.js` first) — passes. Checked for
trailing whitespace directly — none found, matching the commit's own "whitespace validation
passed" claim.

## Verdict

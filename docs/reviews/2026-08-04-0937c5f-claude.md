## Note (non-blocking but worth flagging clearly): export-run inference has no run-scoped key

`_exports` (the temp table mapping this pipeline run to its export_run_id(s)) is built by joining
`v3_unit5_payload_identity` to `export_archive` **only on the natural key**
`(order_item, period, charge_id)` — confirmed by reading `export_archive`'s full column list
(`sql/ddl/048_july_export_shadow_and_archive.sql:7-29`): the table has no `pipeline_run_id` column
at all, so this natural-key join is genuinely the only linking mechanism available in the existing
schema, not an oversight in this file specifically. The risk: if the same `(order_item, period,
charge_id)` triple were ever exported under an *earlier* pipeline run (e.g., a period somehow
re-enters payload_identity for a later run after already being archived once), this procedure would
attribute that stale `export_run_id`/manifest to the *current* run's completeness snapshot, even
though the current run made no new export. Both tables already carry a `payload_hash` column that
isn't used in the join — adding `AND i.payload_hash = a.payload_hash` would close this gap cheaply
and should be considered before this becomes the input to human alerting. Not blocking now because
this file only builds an evidence snapshot (no alert, no export, no GCS write per its own header),
but the risk should travel with the artifact into the eventual alert-delivery review rather than
being rediscovered there.

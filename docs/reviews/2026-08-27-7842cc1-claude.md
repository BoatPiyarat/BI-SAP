## What this does

A pure registration adapter: it backfills a `v3_flow_export_claim` row (`claim_state='DELIVERED'`)
for a Scenario 1 delivery that already happened manually via `v3_onetime_manual_delivery_evidence`
(DDL 086), so that already-delivered flow now shows up in DDL 100's common lifecycle view. It
performs no export, GCS write, or delivery of its own — purely retroactive bookkeeping.

## Verification performed

- **Schema binding.** I checked every column DDL 101 reads from
  `v3_onetime_manual_delivery_evidence` (`production_file_name`, `archive_uri`, `data_row_count`,
  `recorded_at`, `pipeline_run_id`, `export_run_id`, `production_uri`, `production_generation`,
  `production_sha256`, `header_column_count`) against that table's actual `CREATE TABLE` in DDL 086
  — all present, no name mismatch.
- **Byte-binding assertions (lines 49-65, 66-80).** Both join `export_file_manifest` and
  `sap_delivery_manifest_v3` back to the manual-delivery evidence on every identity/hash/size field
  they share, requiring exactly one match with a terminal-or-later `delivery_status` — this
  actually re-verifies the manual delivery landed correctly rather than trusting the evidence
  table's self-report.
- **MERGE safety.** The `USING` subquery is constrained to `pipeline_run_id = ... AND
  export_run_id = ...`, and line 44-48 already asserts exactly one evidence row exists for that
  pair, so the MERGE source is guaranteed single-row — no ambiguous-match risk from the
  multi-condition `ON` clause.
- **Exclusivity.** Line 108-113 blocks re-registration against either the same `export_run_id` or
  a non-abandoned claim on the same flow/run, matching the pattern used elsewhere in this project.

No BLOCK on this file's own logic.

## Note — inherits DDL 100's lifecycle-view defect

This adapter's entire purpose is to route Scenario 1 evidence into
`vw_v3_flow_export_lifecycle` (DDL 100), which I BLOCKed separately
(`docs/reviews/2026-08-27-051543b-claude.md`) for a CASE-ordering bug that mislabels a
multiple-LogID/duplicate-import anomaly as ordinary "pending" progress. Since this adapter's
claims flow through that same view, any Scenario 1 delivery that later hits that anomaly would be
equally mislabeled. This isn't a defect in DDL 101 itself, but deploying 101 without the DDL 100
fix means Scenario 1's pickup/import monitoring inherits the same blind spot.

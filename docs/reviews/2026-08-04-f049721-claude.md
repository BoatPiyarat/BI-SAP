## What changed

Adds `manual_export_request` (13 columns: identity/scope/counts/status/timestamps) and two new
statements in `sp_manual_export`: an `INSERT` immediately before the `export_archive` write, and a
matching `UPDATE` immediately after the existing `export_archive` terminal-status `UPDATE`.

## Verification

1. **Placement is post-validation, pre-write.** The new `INSERT` sits after all fail-closed
   `ASSERT`s (scope, spine, PolicyNo/InvoiceNo/date contract, replay refusal) and before the
   `export_archive INSERT`/`EXPORT DATA` — so only a request that already passed every guard gets an
   audit row, matching the request's "every *validated* manual request persists" wording. An invalid
   attempt (failed `ASSERT`) still produces zero audit rows, same as before this delta — that's
   consistent with what was asked and not a regression from this round.
2. **Every field named in the request is captured.** `requested_by` (via `TRIM`, matching the
   `ASSERT`'s own `TRIM` check so the stored value can't silently differ from the validated one),
   `requested_order_items`/`requested_order_ids` (raw, `IFNULL`-guarded), `pipeline_run_id`,
   `export_run_id`, `selected_payload_rows`/`selected_identity_rows` (both already-computed counts,
   not re-derived), and `archive_uri` are all present in the `INSERT` column list, name-matched
   (not positional), so column order doesn't need to match the `CREATE TABLE` declaration.
3. **PREPARING provenance survives a mid-procedure failure.** BigQuery scripting has no
   cross-statement transaction — each `INSERT`/`UPDATE` commits independently. Since the audit
   `INSERT` (`request_status='PREPARING'`) precedes the `export_archive` write and the
   `EXPORT DATA` statement, a failure at either of those later points (e.g. an `EXPORT DATA` error)
   leaves the `manual_export_request` row stranded at `PREPARING` rather than losing it — which is
   exactly the "must retain PREPARING provenance" behavior the request asked to confirm, and traces
   correctly to BigQuery's actual execution model rather than an assumed transaction boundary.
4. **Terminal status naming is consistent.** Both the `export_archive.delivery_status` and
   `manual_export_request.request_status` final `UPDATE`s use the identical literal
   `'ARCHIVED_PENDING_OBJECT_METADATA'`, scoped by the same `export_run_id` — a reader correlating
   the two tables sees matching state, not two different vocabularies for the same event.
5. **No scope creep.** No change to any of the pre-existing `ASSERT`s, the `EXPORT DATA` column
   list, or the replay-refusal logic — this delta is additive only, as its commit message states.

## Minor forward-looking observation (not a new blocking item this round)

A *rejected* manual-export attempt (failing scope/spine/date `ASSERT`s) still leaves no trace of who
attempted it — only successful validations are now audited. That's exactly what was asked for in
this delta, so it's not a gap in this round; flagging only as something a future security-adjacent
review might want (an attempt log independent of validation outcome), not something to hold this
fix on.

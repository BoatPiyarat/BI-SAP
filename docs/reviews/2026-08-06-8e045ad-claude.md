## Required note — a new, real false-positive in the exact safety check this commit adds

Ran the corrected checker live:

```
"workflow_service_account": "projects/pacific-plating-282708/serviceAccounts/919786098205-compute@developer.gserviceaccount.com",
"safety_failures": ["workflow does not use the approved default Compute service account", ...]
```

This is wrong. I confirmed directly (`gcloud workflows describe ... --format="value(serviceAccount)"`)
that the *real* field value is `projects/pacific-plating-282708/serviceAccounts/<email>` — using the
actual project ID, not a `-` wildcard. The script's normalization,
`.Replace('projects/-/serviceAccounts/', '')`, only matches the literal substring
`projects/-/serviceAccounts/` — which never occurs in the real value — so it's a silent no-op, and
`$workflowServiceAccountEmail` keeps the full resource-path prefix. Comparing that against the bare
`919786098205-compute@developer.gserviceaccount.com` then always fails, **even though the workflow
has used exactly that service account all along** (confirmed independently via the historical
`UNITS_2_5_ARCHIVE_FAILED` log entry's `principal_subject` field from earlier this session, and via
this same live describe call). The workflow-identity check this commit exists to add cannot
currently pass, ever, regardless of real state.

This is specific to the Workflows `serviceAccount` field's resource-path shape — it does not affect
`check_post_import_activation.ps1`, which reads Cloud Run's `spec.template.spec.serviceAccountName`
(already a bare email, no wrapper) and — I verified by running it — **correctly and accurately**
reports `"dispatcher uses the wrong service account"` / `"watchdog uses the wrong service account"`
right now, because those two Cloud Run services genuinely still run under their old dedicated
identities and haven't been redeployed under this new decision yet. That check is correct; the
workflow-identity check in the *other* script is not.

**Fix**: replace the literal `.Replace('projects/-/serviceAccounts/', '')` with something that
strips any project segment, e.g. `-replace '^projects/[^/]+/serviceAccounts/', ''` or
`.Split('/')[-1]`, then re-verify live.

This is a false *positive* (reports a problem that doesn't exist), which is directionally
fail-closed rather than fail-open — it blocks activation rather than wrongly permitting it — so it
does not block this review's PASS. But it must be fixed before this checker's `safety_passed` value
is trusted, since right now it can never be `true` for the workflow-identity dimension regardless of
real state.

## Verdict

PASS WITH REQUIRED NOTE. The pivot itself is a reasonable, explicitly-scoped response to a real
permission constraint (confirmed empirically earlier this session — neither available account can
mutate IAM), and it genuinely fixes the RQ-2149 crash. But I found a new, real false-positive in
the delivery checker's core new safety check by actually running it against live state — the
workflow-service-account comparison can never pass due to a resource-path-format mismatch, even
though the workflow's actual identity has been correct all along. This needs a follow-up delta and
re-review before the delivery checker's `safety_passed` output is relied upon. No IAM, deploy,
scheduler, workflow execution, GCS, BigQuery, email, or SAP mutation was performed by me in this
review — I only ran the two checkers (themselves read-only) and one `gcloud workflows describe`
read.

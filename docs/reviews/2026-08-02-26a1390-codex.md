## Blocking findings

1. `googleapis.run.v2.projects.locations.jobs.run` requires a `body`; the call supplies only
   `name`. Google documents `body` as required. Add at least `body: {}` and configure an explicit
   connector timeout. The successful response is a long-running `Operation`, so `.name` is the
   operation name, not proven Cloud Run execution provenance; record the execution resource from
   the completed response as well. Source:
   https://cloud.google.com/workflows/docs/reference/googleapis/run/v2/projects.locations.jobs/run
2. “Exactly-one loader commitment” is not implemented. Bronze deletion only proves consumption;
   incident evidence already established that outer status/deletion is not a LOAD-job audit.
   Before mirror refresh, require exactly one matching BigQuery LOAD job and record job ID,
   destination, source generation, `outputRows`, `badRecords`, and terminal success. Fail on zero,
   multiple, or mismatched generation/jobs.
3. `post_count == 0` is labelled `HEALTHY_ZERO` from absence alone. Project rules require extract
   success marker + watermark advance + `caught_up=True`; login failure also produces zero rows.
   Read and gate those exact signals before declaring healthy zero.
4. `pipeline_run_log.status` is defined as `SUCCESS | FAILED`, but every transition writes `INFO`.
   The claim also says every transition records upstream IDs/counts while the rows leave
   `rows_in/rows_out` NULL and put partial text in `error_message`. Align schema/semantics and store
   the promised provenance durably.
5. `jobs.query` can return `jobComplete=false` while the BigQuery job continues. Failing the
   workflow at that point permits a replay to overlap the still-running mutating CALL. Poll
   `getQueryResults`/job status to a terminal state (or cancel and verify cancellation), inspect
   terminal errors, then log success. Google explicitly requires polling when incomplete:
   https://cloud.google.com/workflows/docs/reference/googleapis/bigquery/v2/Overview

## CRITICAL — DDL 072's execution-name regex rejects every real execution name (blocks activation)

While verifying this runbook's IAM condition (`resource.name.startsWith('$workflowPrefix')`,
built from `$projectNumber = '919786098205'`), I checked what a *real* Workflows execution's
canonical resource name actually looks like:

```
gcloud workflows executions describe a6cf3e66-3cfc-49d1-8ae3-bb1c6696c36a \
  --workflow=v3-nightly-orchestrator --location=asia-southeast1 \
  --project=pacific-plating-282708 --format="value(name)"
→ projects/919786098205/locations/asia-southeast1/workflows/v3-nightly-orchestrator/executions/a6cf3e66-...
```

**The real resource name uses the numeric project number, not the project ID string.** This
runbook's IAM condition correctly uses `$projectNumber` — it is right. But
`sql/ddl/072_v3_post_import_refresh_dispatch.sql`'s `sp_bind_v3_post_import_execution` (reviewed
and passed in RQ-20260805-1928) asserts:

```sql
ASSERT REGEXP_CONTAINS(p_workflow_execution_name,
  r'^projects/[a-z][a-z0-9-]{4,28}[a-z0-9]/locations/[a-z0-9-]+/workflows/[A-Za-z0-9_-]+/executions/[A-Za-z0-9_-]+$')
```

This pattern requires the project segment to *start with a lowercase letter* — it can never match
a numeric project number. The workflow constructs its own `workflow_execution_name` via
`sys.get_env("GOOGLE_CLOUD_PROJECT_ID")` — and GCP Workflows' own runtime environment variable of
that name is documented to return the **numeric project number**, not the project-ID string,
despite its name (a well-known, frequently-noted GCP Workflows quirk). This is consistent with the
empirical resource name I just pulled directly from the live API above.

**If this is correct — and both the live evidence and the documented behavior of this specific
environment variable point the same way — every single real self-bind call would fail its own
format assertion, every time, with no exception.** The practical consequence: Unit 1 would run to
completion, but `sp_bind_v3_post_import_execution` would throw on the very first real call,
`gate_post_import_contract`'s downstream logic would never see a matching binding, and the outbox
row would sit `CLAIMED` forever until the watchdog's `CLAIM_TIMEOUT_SECONDS` (600s) releases it for
a retry that would fail identically — every request eventually exhausting to `HUMAN_ACTION` after
three attempts. The entire post-import pipeline would be silently, completely non-functional end
to end, even though every individual reviewed component (DDL 072's *other* assertions, the
dispatcher, the watchdog, this admin runbook) is independently correct.

I cannot generate a real execution to conclusively prove `sys.get_env("GOOGLE_CLOUD_PROJECT_ID")`'s
exact return value without executing the workflow, which is outside this review's boundary. But
the live resource-name evidence is unambiguous, and it directly contradicts DDL 072's regex. **This
needs to be resolved with certainty (checked against GCP's current documentation, or proven via a
disposable, delivery-disabled synthetic execution during the already-planned rehearsal) before this
admin runbook is run** — running it would correctly wire up IAM into a pipeline that cannot
complete a single successful bind.

**Recommendation**: loosen DDL 072's regex to accept a purely numeric project segment
(e.g. `^projects/[a-zA-Z0-9][a-zA-Z0-9-]{4,28}[a-zA-Z0-9]/locations/...`), or explicitly confirm via
GCP's Workflows documentation/a synthetic rehearsal execution which literal value
`sys.get_env("GOOGLE_CLOUD_PROJECT_ID")` returns in this project, then adjust whichever side is
wrong. This should be a new Class-A delta request against DDL 072, reviewed before activation.

## Checked against this request's own checklist (the runbook itself)

- **PowerShell quoting and failure boundaries**: backtick line-continuations are used correctly
  throughout; the dispatcher URL resolution checks both `$LASTEXITCODE` and a non-empty result
  before use; the scheduler create/pause steps each have an explicit `throw` on failure — critically,
  the pause-step throw message ("stop and inspect immediately") reflects that a failed pause after
  a successful create is the one place a silent failure could leave a job on a schedule other than
  intended. The final cadence `update` has no explicit failure check, but its failure mode is inert
  (stays `PAUSED` with the old dormant schedule) and is independently caught by
  `check_post_import_activation.ps1`'s cadence check (reviewed in RQ-2035) — not a gap worth
  blocking on.
- **Custom permission/condition correctness**: `postImportWorkflowCreator`
  (`workflows.executions.create` only) and `postImportWorkflowMonitor`
  (`workflows.executions.get`, `workflows.executions.cancel` only) are each scoped to exactly the
  permissions their name implies, with no extra grants. The condition's `resource.name.startsWith`
  prefix is built from `$projectNumber`, which — per the finding above — is actually the *correct*
  choice given real resource-name format, unlike DDL 072's regex.
- **BigQuery routine/table roles**: project-level `bigquery.jobUser` for both runtimes is granted
  unconditionally (correctly, since both need to submit jobs); the table-level `dataEditor` grant on
  exactly `v3_post_import_refresh_outbox` (not dataset-wide) is explicitly gated behind "only after
  Boat explicitly approves that risk," and the routine-level `dataViewer` grants are scoped to the
  exact four procedures each identity actually calls — matching what I traced in the DDL 072/073
  reviews (dispatcher calls claim/release; watchdog calls release/complete).
- **Pub/Sub service-agent grants**: `roles/pubsub.publisher` to the Pub/Sub service agent on the
  DLQ topic is the standard, necessary grant for dead-letter forwarding to function at all;
  `roles/iam.serviceAccountTokenCreator` on the push service account for the same agent is the
  standard grant needed for Pub/Sub to mint OIDC tokens as that identity for authenticated push.
- **Push endpoint/audience**: `--push-auth-service-account=$pushSa --push-auth-token-audience=
  $pushEndpoint` where `$pushEndpoint = "$dispatcherUrl/dispatch"` — matches exactly what
  `check_post_import_activation.ps1`'s corrected delta (`aae4e01`, reviewed in RQ-2035) validates.
- **DLQ forwarding**: `--dead-letter-topic=sap-post-import-refresh-dlq --max-delivery-attempts=5` —
  matches the checker's expected values exactly.
- **Scheduler OAuth endpoint/body and pause-before-cadence behavior**: the `:run` URI
  (`.../namespaces/$projectNumber/jobs/${watchdog}:run`) matches the checker's own expected URI
  construction exactly; `--oauth-service-account-email=$watchdogSa` with
  `--oauth-token-scope=cloud-platform` is the standard pattern for Scheduler→Cloud Run Jobs
  invocation (the broad OAuth *scope* is a normal requirement of this specific call shape; actual
  authorization is separately and correctly constrained by the narrow `run.invoker`-on-one-job IAM
  grant, confirmed already absent/to-be-added, not broadened). The create→pause→update-cadence
  sequence is the correct workaround for Cloud Scheduler's lack of a create-paused flag, verified:
  `gcloud scheduler jobs create http --help` confirms `--attempt-deadline` and `--oauth-token-scope`
  are real flags; `gcloud pubsub subscriptions create --help` confirms `--min-retry-delay`,
  `--max-retry-delay`, and `--expiration-period` are real flags.
- **Checker compatibility**: every value this runbook would produce (topic names, push endpoint,
  OIDC audience/service account, DLQ topic/attempts, ack deadline, scheduler cadence/URI/OAuth
  identity) matches field-for-field what `check_post_import_activation.ps1`'s corrected delta
  actually validates — the two artifacts are consistent with each other.
- **This artifact performs no IAM/resource mutation**: confirmed — it is a Markdown document with
  embedded PowerShell code blocks; reviewing and reading it does not execute anything. I did not run

## Verdict

The runbook itself is well-constructed, internally consistent with everything already reviewed,
and correctly uses the project number where DDL 072 does not. **Do not run this runbook until the
DDL 072 regex/project-identifier mismatch above is resolved** — as written, running it would
correctly grant IAM into a pipeline whose self-bind step would then reject every real call. No
mutation was performed by me in this review.

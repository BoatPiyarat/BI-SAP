# Review — RQ-20260805-1928-post-import-dispatch-transitions

## Checked against the request's own checklist

- **Exact-key, claim-token and execution-name uniqueness**: `sp_claim_v3_post_import_refresh`
  requires exactly one outbox row for `(log_id, export_run_id, sap_file_name)` and asserts the
  `claim_token` isn't already bound to a *different* `log_id`. `sp_bind_v3_post_import_execution`
  separately asserts the `workflow_execution_name` isn't already bound to a different `log_id`.
  Both are checked before their respective transactions open.
- **Concurrent/duplicate claim and bind behavior — traced the full race**: claim uses a
  deterministic `claim_token` (same triple → same token), so two concurrent claim calls for the
  same event only ever let one `UPDATE` actually flip `PENDING→CLAIMED`; the loser's `UPDATE`
  affects 0 rows, but the idempotency assert (`COUNT(... claim_token=p_claim_token AND
  request_status IN ('CLAIMED','STARTED'))=1`) still passes for the loser because the row is
  genuinely bound to *the same token* — both callers see success and proceed. The real
  duplicate-execution race then happens at bind time: `sp_bind_v3_post_import_execution`'s `UPDATE`
  only transitions from `CLAIMED`, so only one of two racing binds actually writes; **both** binds
  now (`cbdf430`'s fix) read back the row via a post-commit `SELECT` regardless of whether their own
  `UPDATE` matched, so the loser learns the *winning* `workflow_execution_name` instead of
  asserting its own intended value and failing. This is exactly what lets the calling workflow
  (reviewed under RQ-1939 below) detect "I lost" and exit cleanly instead of raising.
- **Release and attempt-three boundary**: `sp_release_v3_post_import_claim` requires a non-empty
  ≤300-char sanitized error template, only touches rows still `CLAIMED`, and sets
  `PENDING`/clears `claim_token`+`claimed_at` when `attempt_count<3`, or terminalizes to
  `HUMAN_ACTION` with `completed_at` set and the identifying fields *preserved* (not cleared) when
  exhausted. Traced the counting: `claim()`'s own `UPDATE` only fires under `attempt_count<3`
  and increments by exactly 1 each time, so attempt_count can reach at most 3 — the "stop at three"
  bound is real, not just asserted.
- **Terminal transition/error-template rules**: `sp_complete_v3_post_import_refresh` restricts
  terminal status to `SUCCEEDED`/`TIMEOUT`/`HUMAN_ACTION`, enforces success⇔no-error and
  failure⇔sanitized-error-required as a single paired assertion, and only transitions from
  `STARTED`, matched by `(log_id, workflow_execution_name)` rather than the claim token (correct —
  by completion time the caller knows its own execution name, not necessarily the original token).
- **Transaction row-count guards**: every procedure wraps its write in `BEGIN
  TRANSACTION`/`COMMIT TRANSACTION` with an `ASSERT @@row_count` immediately after the `UPDATE` —
  `IN (0,1)` where 0 is a legitimate idempotent-duplicate outcome (claim, bind), `=1` where the
  call is expected to always affect exactly one matched row (release, complete). An uncaught
  assert failure anywhere after `BEGIN TRANSACTION` rolls back the whole transaction per this
  project's established BigQuery multi-statement semantics.
- **The two corrective deltas are exactly what they claim**: `785f62e` splits the original
  single `sp_claim_v3_post_import_refresh` (which took `workflow_execution_name` as an input and
  set `STARTED` directly) into a separate claim/bind pair — correcting the flawed assumption that
  an execution name exists *before* the Workflows create call, which is impossible since the
  Executions API assigns that name server-side. `cbdf430` removes the old "assert my own write
  won" check from bind and replaces it with the read-back-and-return pattern described above —
  making the post-create self-bind duplicate-safe rather than failure-prone under a genuine race.
- **No workflow, topic, delivery, ACK, or SAP action occurs**: this is a DDL/procedure source file;
  reviewing it does not execute anything. Independently re-ran the mandatory dry-run —
  0 bytes, matching the commit's own claim.

## Verdict

PASS. The claim→bind→release/complete state machine is sound, including the one genuinely hard
part (duplicate Workflows executions racing to bind) — both callers now read back the same
authoritative winner rather than each asserting their own outcome. No BigQuery mutation beyond the
dry-run, no deployment, and no production action occurred in this review.

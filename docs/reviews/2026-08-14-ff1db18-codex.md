## Standards

1. The ICT month boundary is wrong. `TIMESTAMP(DATE_TRUNC(CURRENT_DATE('Asia/Bangkok'), MONTH))`
   interprets the resulting DATE at UTC midnight, excluding 00:00–06:59 ICT on the first day.
   There is also no upper bound, so future-dated rows can enter MTD.
2. `buildReconMtdReport_()` runs before the mail `try`; BigQuery/API/JSON/report failures never
   reach the fallback channel. Only primary-mail failure does.
3. The exact production SQL has no successful mandatory dry-run. On 2026-08-14 the safe-wrapper
   probe still failed with `ReauthUnattendedError` from legacy `bq 2.0.92`.
4. The deployment contract has no exact Script ID, manifest/timezone change, property commands,
   trigger creation/verification, captured trigger ID, or <5-minute rollback procedure. No browser
   session or authenticated `clasp` is available on this machine, so guessing a project is unsafe.

No actionable Fowler smell was found. The query is partition-prunable, selects only required
columns, and caps billing at 20 GiB. No secret is committed. The exact offline source parse and
contract harness passed: `daily_recon_mtd_report local contract tests: 10 assertions passed`.

## Spec

1. BigQuery HTTP 200 with `jobComplete:false` is a normal asynchronous response, but the source
   throws instead of polling `jobs.getQueryResults`; page tokens are also unsupported.
2. Unexpected `recon_status` values are collected then silently omitted from the three rendered
   rows, allowing plausible incomplete totals after schema drift.
3. Recipient distinctness compares raw strings only; case/whitespace variants of the same mailbox
   pass.
4. Apps Script time-driven `nearMinute(0)` execution is an execution window, not an exact 06:00
   guarantee; the contract must state and verify the accepted window.
5. “Always reads same-night data” is unsupported without a freshness gate on `recon_checked_at`.

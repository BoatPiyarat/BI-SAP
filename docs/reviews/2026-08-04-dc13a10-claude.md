# Review — RQ-20260804-2040-manual-sync-empty-bronze-prefix

Reviewer: Claude Code
Artifact: commit `dc13a10`; `scripts/run_sap_sync_manual.ps1`.
Verdict: **PASS**

## What changed

`Get-BronzeObjects` wraps `& gsutil ls $bronzePath 2>$null` in a `try/finally` that temporarily
sets `$ErrorActionPreference = 'Continue'` for the duration of the call, restoring the prior value
immediately after. Three call sites change `$objects = Get-BronzeObjects` to
`$objects = @(Get-BronzeObjects)`.

## Verification — the stderr/ErrorActionPreference bug is real, and the fix is correctly scoped

The script sets `$ErrorActionPreference = 'Stop'` and `Set-StrictMode -Version Latest` at file
scope. In Windows PowerShell 5.1, redirecting a native command's stderr (`2>...`, including
`2>$null`) causes each stderr line to be wrapped as a `NativeCommandError` `ErrorRecord`; under
`$ErrorActionPreference = 'Stop'`, that record becomes a *terminating* exception at the point of
the call — independent of the exit code, and independent of the redirection target discarding the
line's text. `gsutil ls` on an empty prefix writes `CommandException: One or more URLs matched no
objects.` to stderr and exits 1 — exactly the case the function's own `if ($LASTEXITCODE -notin 0,
1)` line was written to treat as valid. Before this fix, that line was unreachable for the
empty-prefix case: the call itself would throw first. The local `Continue` override is scoped
tightly (only around the one `& gsutil ls` invocation, restored via `finally` even on an unrelated
exception) and does not weaken the actual safety check — `$LASTEXITCODE -notin 0, 1` still throws
for any exit code other than 0 or 1, so a real gsutil failure (auth error, network error, wrong
bucket) still stops the script.

Checked whether this same stderr-wrapping bug could recur elsewhere in the file: every other native
call in the script (`gcloud run jobs execute`, `gcloud scheduler jobs run`, both `bq query`
invocations) runs without stream redirection, so none of them hit the same mechanism — the bug is
specific to redirected stderr, and `Get-BronzeObjects` was the only call site redirecting it. No
follow-on note needed.

The `@(...)` wrapping fix is the standard, correct fix for PowerShell's single-object pipeline
unwrapping: even though `Get-BronzeObjects` returns `@($output | Where-Object { $_ })` internally,
a single-element array emitted through a function's output stream is enumerated and collapses to a
scalar at the caller under `Set-StrictMode`, which would make `.Count` fail exactly when exactly
one bronze object is pending — the one-object case that matters most for this script's logic
(`$objects.Count -eq 1` gates the loader-trigger branch). Re-wrapping at all three call sites
closes that gap consistently.

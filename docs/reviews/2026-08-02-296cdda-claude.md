## NOTE 1 (required): declare the dropped live wrapper

The live view carries an outer `SELECT * REPLACE(... AS BatchRunDate, ... AS PaymentDate)` hotfix
wrapper (comment-tagged "RULE-02") that 050 removes. Removing it is **correct** — 048 overrides
both fields properly downstream (`PaymentDate` from `expected_state`'s RULE-01 clamp;
`BatchRunDate` = `LAST_DAY(open_period)`), so the wrapper must not double-apply — but the header
claims "differences are intentionally narrow" and lists only two. For a baseline-derived
money-bearing source, declared-deviation completeness is the entire audit value: add the third
bullet.

## NOTE 2 (separate finding — legacy lane, Boat decision): the live wrapper is itself buggy

Verified from the live definition: the wrapper computes
`SAFE.PARSE_DATE('%d%m%Y', '2026-07-31')` — an ISO literal parsed with a DDMMYYYY format —
which is **always NULL**, so live `BatchRunDate` evaluates to
`IF(unparseable → NULL, GREATEST(date, NULL) → NULL)` = **NULL for every row** in the production
view, today. (The PaymentDate arm is fine — it uses `DATE '2026-07-01'` correctly.) 050/048 are
unaffected (both fields overridden), but any *other* consumer of the live view is currently
reading NULL BatchRunDate. Owner decision needed: fix the literal to `'31072026'` or revert the
hotfix wrapper. This also likely explains part of the Aug-1 drift-inventory result for this view.

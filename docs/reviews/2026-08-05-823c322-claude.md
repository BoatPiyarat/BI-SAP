## Checked against the request's own checklist

- **Exact LogID/export/filename/header/outbox binding**: `sp_reconcile_v3_post_import_rows`
  requires exactly one `STARTED` outbox row for `(log_id, export_run_id, sap_file_name)`, exactly
  one matching `sap_import_result_header_v3` row (`company_db='RCB_LIVE_DB'`,
  `attachment_parse_status='PARSED'`, non-empty `txt_gcs_uri`, terminal status), and exactly one
  matching `sap_delivery_manifest_v3` row across the full set of "already delivered or further
  along" statuses. All three are asserted before any temp table or write.
- **Child `UNIT1_COMPLETE` proof**: `ASSERT (SELECT COUNT(*) FROM pipeline_run_log WHERE
  run_id=p_child_pipeline_run_id AND step='UNIT1_COMPLETE' AND status='SUCCESS')=1` — the *child*
  execution's own run_id, passed by the calling workflow as `run_id` (its own), which by this point
  in the YAML has already logged its own `UNIT1_COMPLETE` success earlier in the same execution.
  Self-consistent: reconciliation cannot run before the workflow's own Unit 1 evidence exists.
- **Archive key and manifest row conservation — traced every guard**: `_archive` is bounded to
  `DELIVERED`/`PICKED_UP` rows for the export run; asserts a non-zero, non-duplicated
  `(order_item,period,charge_id,payload_hash)` key; cross-checks the *manifest's own* recorded
  `data_row_count` equals the live archive count (`v_rows`) — a genuine drift check, not just an
  assumption. After classification, `ASSERT v_rows=v_acknowledged+v_rejected+v_pending` is the core
  conservation invariant; the later `@@row_count=v_rows` asserts on both the reconciliation-table
  insert and the `export_archive` update confirm every archived row actually received evidence and
  an update, not just that the counts summed correctly in memory.
- **Exact error precedence**: the outcome `CASE` checks `exact_error_detail_count>0` before
  `mirror_docentry IS NOT NULL` — an explicit SAP row-level error always wins over an apparent
  mirror match. `_exact_errors` groups by `(order_item, period)` only, which is coarser than the
  full `(order_item,period,charge_id,payload_hash)` archive key — a structural limit of
  `sap_import_error_detail_v3`'s own schema (no charge/payload columns), not something this
  procedure could narrow further. Worth flagging (not blocking): a stale row-level error from an
  earlier charge/payload on the same `(order_item, period)` could still shadow a genuinely
  acknowledged newer charge on that same period, since the join key can't distinguish them.
- **Mirror match tuple/status**: `_mirror_match` joins on `U_OrderItem`, `U_Period`, `U_InvoiceNo`
  (both sides `IFNULL`'d to `''` for a clean equality), and case-insensitive `TransactionStatus` —
  matching the *expected* identity and status from the delivered payload, not just row presence —
  then `QUALIFY ROW_NUMBER() ... ORDER BY UpdateDate DESC, UpdateTime DESC, DocEntry DESC = 1` picks
  the single latest mirror row if more than one matches. Confirmed live:
  `sap_integration_v3.sap_mirror_doc` has exactly the columns referenced
  (`U_OrderItem`, `U_Period`, `U_InvoiceNo`, `TransactionStatus`, `UpdateDate`, `UpdateTime`,
  `DocEntry`); `export_archive` has `sap_log_id`, `sap_result_status`, `acknowledged_at`,
  `delivery_status`, `payload_json`, `payload_hash`, `order_item`, `period`, `charge_id`,
  `export_run_id` — all live, matching what the procedure reads and writes.
- **Idempotent rerun behavior**: the reconciliation table write is `DELETE ... WHERE (log_id,
  export_run_id)` then `INSERT` — a clean replace, not an accumulate. The `export_archive` update's
  `acknowledged_at` uses `IFNULL(a.acknowledged_at, CURRENT_TIMESTAMP())`, so a rerun never bumps an
  already-set acknowledgment timestamp forward. The manifest status update's `WHERE delivery_status
  IN (...)` deliberately includes the terminal statuses themselves, so a rerun after prior evidence
  changes (e.g. a late-arriving mirror row) can safely re-derive and move the manifest status again
  — a deliberate "re-reconcile as evidence improves" design, not an oversight.
- **Atomic ledger transitions**: the reconciliation-table replace and all three downstream updates
  (`export_archive`, `sap_delivery_manifest_v3`, `export_file_manifest`) sit inside one
  `BEGIN TRANSACTION`/`COMMIT TRANSACTION` block with a row-count `ASSERT` after each write — any
  one guard failing rolls back all four writes together.
- **Workflow result decoding**: the YAML's `reconcile_post_import` subroutine reads
  `rows[0].f[0..4]` for `total_rows/acknowledged_rows/rejected_rows/pending_rows/manifest_status`,
  matching DDL 073's final `SELECT v_rows, v_acknowledged, v_rejected, v_pending, v_manifest_status`
  by position exactly.
- **Residual alert path**: `gate_post_import_residual` checks `pending_rows > 0` and, if so, calls
  `complete_post_import(..., terminal_status="HUMAN_ACTION", error_template=
  "ROW_RECONCILIATION_RESIDUAL")` **then** `fail_closed(...)` — confirmed `fail_closed` (a
  pre-existing, already-relied-upon subroutine used elsewhere in this file) logs the failure,
  publishes to the existing `alert_topic` Pub/Sub topic, and unconditionally `raise`s — genuinely
  fails closed and reuses the existing alert channel rather than introducing a new one, matching the
  claim precisely. Zero residual instead calls `complete_post_import(..., "SUCCEEDED", null)`.
- **No GCS, delivery, workflow execution, SAP action, deployment, or procedure CALL occurred**:
  DDL 073 is a new table plus one procedure (source only); the YAML delta is source. Independently
  re-ran the mandatory dry-run — 0 bytes — and `git diff --check` on both commits — clean.

## Verdict

PASS. Row conservation is genuinely enforced end to end (archive→reconciliation table→three ledger
updates, all atomic), the error-precedence and mirror-match logic are exact rather than approximate,
and the residual/alert path correctly reuses the existing fail-closed mechanism. One non-blocking
observation: `sap_import_error_detail_v3`'s `(order_item, period)`-only grain is a structural limit
of the source data, not a defect in this procedure. No SAP, GCS, delivery, or workflow-execution
action is requested or occurred in this review.

## BLOCK 1 — watermark advance is invalid SQL (CONFIRMED, not speculative)

```sql
SET (new_wm_date, new_wm_time) = (
  SELECT AS STRUCT MAX(UpdateDate), MAX(IF(UpdateDate = MAX(UpdateDate) OVER(), UpdateTime, NULL))
  FROM delta
);
```
Reproduced the construct as a standalone dry-run (2026-08-01, 0 bytes):
`bq query --dry_run 'SELECT AS STRUCT MAX(d), MAX(IF(d = MAX(d) OVER(), t, NULL)) FROM (SELECT CURRENT_DATE() AS d, 1 AS t)'`
→ **`Error in query string: Analytic functions cannot be arguments to aggregate functions`**.

Consequence if deployed as-is: statements in a procedure run sequentially, so the MERGE commits,
**then** the SET fails → every run errors *after* mutating the mirror, and the watermark never
advances (each night re-scans and re-merges the same delta; correct-but-degenerate at full-scan cost,
plus a nightly ERROR in the chain).

Fix (one statement, same semantics):
```sql
SET (new_wm_date, new_wm_time) = (
  SELECT AS STRUCT UpdateDate, MAX(UpdateTime)
  FROM delta
  WHERE UpdateDate = (SELECT MAX(UpdateDate) FROM delta)
  GROUP BY UpdateDate
);
```

## BLOCK 2 — delta's UpdateDate type no longer matches the mirror it merges into

Post-2c96c53, `024` builds the mirror with `DATE(UpdateDate)` → column type **DATE**. But 043's four
delta branches carry **raw `UpdateDate` (TIMESTAMP** — verified against all four shard schemas via
`bq show --schema`). The MERGE then assigns/inserts TIMESTAMP into a DATE column; BigQuery has no
implicit TIMESTAMP→DATE coercion, so the MERGE fails at CALL time (again invisible to dry-run).

Fix must be coherent end-to-end, because the watermark filter and advance use the same column:
- project `DATE(UpdateDate) AS UpdateDate` in all four branches (the `WHERE UpdateDate > wm_date`
  filter still reads the raw source column, unaffected), **and**
- align the watermark domain: simplest is `last_upd_date DATE` (SAP B1's UpdateDate is
  date-granularity; intra-day recency lives in `UpdateTime`), seeding `DATE '1900-01-01'`.

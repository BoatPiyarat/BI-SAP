- **Identifier derivation against reviewed DDL 074**: compared this file's `_cases` construction
  directly against `sql/ddl/074_post_import_rehearsal_fixtures.sql`'s own `_cases` temp table

  identical constructions. A verifier built from a copy-pasted, drifted derivation would silently
  check the wrong rows; this one matches exactly.
- **Partition bounds**: `outbox`/`row_result`/`archive`/`sap_manifest` each filter
  `DATE(...) >= DATE_SUB(CURRENT_DATE('Asia/Bangkok'), INTERVAL 2 DAY)` on their respective
  partitioned timestamp columns — a reasonable, cost-bounded window for a same-day/next-day

  the `export_run_id` filter already lets clustering prune effectively.
- **Join grain and duplicate risk**: all joins are `LEFT JOIN ... USING(log_id, export_run_id)` or
  `USING(export_run_id)`. None of `v3_post_import_refresh_outbox`, `export_archive`,
  `sap_delivery_manifest_v3`, or `export_file_manifest` has a schema-enforced uniqueness constraint
  on those keys in general — but for *these specific* rehearsal identifiers, DDL 074 only ever
  seeds exactly one row per synthetic `export_run_id` in each of those tables (confirmed in the
  RQ-2051 review), so no fan-out is possible here. This is a safe assumption for a rehearsal-only
  verifier working exclusively against nonce-unique fixture data, not a generically safe pattern —
  worth noting if this query is ever repurposed against real production identifiers, but not a
  defect as written.
- **NULL behavior of `expected_final_state` — traced through SQL's three-valued logic
  explicitly, not assumed**: the column is a chain of `AND`-ed equality/`IS NULL` checks. If a
  joined row is entirely absent (nothing has run yet), every comparison against that row's columns
  evaluates to `NULL` (not `FALSE`), and `NULL AND NULL = NULL` — so the result surfaces as `NULL`,
  visibly distinct from `true`, never mistakable for success. If evidence exists but is genuinely
  wrong (e.g. outbox still `PENDING` when `SUCCEEDED` is expected), that specific comparison is a
  real `FALSE`, and `FALSE AND anything = FALSE` in three-valued logic regardless of other `NULL`
  terms — so a partially-complete state also cannot show `true`. The column can only ever be `true`
  when every joined value is present and every check passes.
- **Exact ACK/REJECT/RESIDUAL expectations — traced against DDL 073's actual UPDATE logic, not just
  described**: the `CASE c.case_name` block requires ACK → `sap_result_status='ACKNOWLEDGED'` and
  `acknowledged_at IS NOT NULL`; REJECT → `sap_result_status='REJECTED'` and `acknowledged_at IS
  NULL`; RESIDUAL → both `NULL`. Cross-checked against `sp_reconcile_v3_post_import_rows`'s

  outcome, including REJECTED. Both match this verifier's expectations exactly.

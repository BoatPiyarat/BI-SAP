## Checked — healthy-zero vs. terminal-nonzero ordering, the finding's central technical claim,
traced against the actual procedure code rather than taken on description

`sp_build_v3_daily_completeness_snapshot`'s `SAP_RESULT` metric is built from
`IFNULL(a.sap_result_status, 'PENDING_ACK')` against `export_archive` — and `export_archive.
sap_result_status` is only populated by DDL 073's reconciliation (reviewed in RQ-1946), staying
`NULL` (→ `PENDING_ACK`) until that reconciliation actually runs. Critically, the procedure's own
guard — `ASSERT (SELECT COUNT(*) FROM v3_daily_completeness_run WHERE pipeline_run_id=...) = 0 AS
'completeness snapshot already exists; immutable replay refused'` — means **there is no second
chance**: a snapshot taken before reconciliation completes permanently records `PENDING_ACK` with
no update-in-place and no allowed re-run for that `pipeline_run_id`. This independently confirms
the finding's core claim in the strongest possible way — not just "could be stale" but "would be
permanently wrong, unfixable for that run."

## Checked — the new item 3 (pipeline-run binding), added in this exact delta, is a sharp and
correct catch, not filler

The finding points out the outbox/manifest carries `export_run_id`, not the *original outbound*
`pipeline_run_id` DDL 067 requires, and that the post-import *child* execution's own
`pipeline_run_id` must never be substituted. I verified why this matters concretely: post-import
mode returns before Units 2–5 (confirmed in the RQ-1939/1946 reviews' `stop_after_post_import_unit1`
tracing), so a child execution's `pipeline_run_id` would never have rows in `v3_unit2_summary`,
`v3_unit2_magnitude_run`, or `v3_notification_run_summary` — meaning DDL 067's own preconditions
(lines 67–75) would hard-fail if anyone naively passed the child's ID. The finding correctly
identifies this as something needing an explicit binding design, not something to paper over.

## Checked — the delta itself is a genuine correction, not just added detail

Diffed `a6bc76e` against its parent: the *original* ordering said a snapshot could follow "the
zero-file or exact delivered-manifest outcome is final" — treating `DELIVERED` as sufficient. The
corrected version explicitly rejects that (`DELIVERED`/`PICKED_UP` is not terminal; only
`ACKNOWLEDGED`/`PARTIAL_REJECT`/`REJECTED` with `pending_rows=0` is) — this is exactly the
healthy-zero-vs-nonzero distinction verified above, so the correction is substantively right, not
cosmetic.

## Finding

The evidence narrows what `data@rabbit.co.th` can author, but it does not prove that two runtime
blockers “can proceed.” Authenticated Pub/Sub push also requires topic attachment permission,
`iam.serviceAccounts.actAs`, effective OpenID-token minting by the Pub/Sub service agent, and the
push identity's Cloud Run invoker binding. DLQ configuration can require further publisher/
subscriber bindings. The recorded tests do not prove those effective bindings. Likewise,
Cloud Scheduler job create/update plus `actAs` does not prove the selected runtime identity can
invoke the watchdog target. The design's no-`run.invoker` statement conflicts with official Cloud
Run/Pub/Sub authentication requirements and must not be treated as settled.

Authoritative references: Google Cloud's authenticated-push documentation requires the Pub/Sub
service agent to mint OIDC tokens and the push service account to hold Cloud Run Invoker; the push
subscription creation contract also requires `pubsub.topics.attachSubscription` where applicable.
The artifact should distinguish “operator may create/update configuration” from “end-to-end runtime
is ready.”

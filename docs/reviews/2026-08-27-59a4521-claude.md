## Prior BLOCK items — verified each is actually closed, not just claimed closed

1. **Terminal classification (PICKED_UP wrongly excluded as terminal).** Fixed. DDL 103's `_hold`
   CASE now has three separate branches: `sap_result_status='ACKNOWLEDGED'` →
   `NOT_EXPORT_TERMINAL_ACKNOWLEDGED` (genuinely terminal, correctly excluded from re-export);
   `delivery_status IN ('DELIVERED','PICKED_UP')` without ack →
   `NOT_EXPORT_PENDING_TERMINAL_ACK` (held, not silently treated as terminal); `REJECTED`/
   `PARTIAL_REJECT` → its own branch. The checker independently greps for both string literals
   (`check_v3_monthend_onetime_snapshot.py:30-32`), so this can't silently regress.
2. **Implicit `SELECT c.*` contract.** Fixed. Both DDL 103's final SELECT and the operator's final
   SELECT enumerate the exact 56 columns positionally; the checker parses the operator's final
   SELECT and asserts exactly 56 columns with the correct first-4/last-4 names
   (`check_...py:55-64`). Ran it locally — genuinely PASSes, not aspirational:
   `V3_MONTHEND_ONETIME_STATIC=PASS`, `V3_MONTHEND_ONETIME_EXPORT_COLUMNS=56`.
3. **Final output lacked re-asserted invariants.** Fixed. The operator re-derives and re-checks
   population conservation, manifest/payload/identity count parity, the 56-column positional
   contract via live `INFORMATION_SCHEMA.COLUMNS`, duplicate-identity, flow/hash consistency, the
   Paid/Period/length contract, date format, and payload/hold disjointness — all against
   `_target_payload`/`_target_identity`/`_target_hold`, i.e. the actual rows about to be exported,
   not an intermediate table.
4. **Held rows not durable.** Fixed. `v3_monthend_onetime_hold` is a real durable table, written
   inside the same transaction as the payload, with a build-time ASSERT
   (`Every event must end in the immutable payload or durable hold`) and an operator-side ASSERT
   that the payload and durable hold never intersect.
5. **TOCTOU / no immutable snapshot identity.** Fixed. This is the core of the redesign: DDL 103
   builds and commits a named, hash-bound, partitioned snapshot once; the operator only ever reads
   back `target_snapshot_run_id`'s own rows, filtered to its own `built_at`/`detected_at` partition
   date. Re-running the operator against the same `snapshot_run_id` cannot yield a different
   population.
6. **Missing safe-query wrapper / cost ceiling instruction.** Fixed — operator header now
   mandates `scripts/bq_safe_query.sh` and explicitly forbids direct `bq query`; checker greps for
   both strings.
7. **UTC vs ICT month boundary.** Fixed. `DATE(e.charge_time,'Asia/Bangkok')` replaces the bare
   `DATE(charge_time)` for both the event filter and `source_payment_date_ict`. Checker greps for
   the ICT form and greps *against* the presence of the old UTC form in the DDL, so a regression
   back to UTC would fail the static gate, not just go unnoticed.

## What I additionally traced (the request's specific spec/standards questions)

- **Hold-join fan-out risk.** `_hold` LEFT JOINs `_events` against `_ready_identity`,
  `_latest_archive` (deduped via `ROW_NUMBER() ... =1`, so ≤1 row per key — safe), `_ddl085_hold`
  (`GROUP BY` to the same key — safe), and `_validation_hold` via
  `USING(order_item,period,invoice_no)`. The last one is the one genuine open question: nothing in
  this file *proves* `(order_item,period,invoice_no)` is unique the way
  `(order_item,period,charge_id)` is proven unique (line 172-174's explicit ASSERT). If two charges
  in the same order_item+period ever shared an `invoice_no`, `_hold` would fan out and the
  population-conservation ASSERT (`COUNT(_events)=COUNT(_ready)+COUNT(_hold)`) would fail loud
  rather than silently overcounting — so this is fail-closed even if the assumption is wrong, not
  a silent-corruption risk. Consistent with every other flow in this project binding invoice_no
  1:1 to charge identity via `fn_invoice_no()`, but not independently re-verified against live
  data this session.
- **Bijective binding, no silent downgrade.** `_ready_match` joins DDL 085's ready payload back to
  its own identity row and re-checks `TO_HEX(SHA256(TO_JSON_STRING(p)))=i.payload_hash` — this is
  the mechanism that prevents building a snapshot against a DDL 085 payload that has drifted since
  its hash was recorded. Directly answers the request's "can the DDL 085 binding silently
  downgrade or misclassify any event" — no, a hash mismatch means the row simply fails to join and
  falls through to `_hold` as `HOLD_UNCLASSIFIED_PIPELINE_GAP` rather than being silently accepted.
- **CTAS/partitioning mechanics.** `CREATE TABLE IF NOT EXISTS ... PARTITION BY DATE(built_at) ...
  AS SELECT ... WHERE FALSE` is valid BigQuery syntax for declaring a partitioned/clustered schema
  with zero rows and no side effect — confirmed this is the same idiom used elsewhere in this
  project, not a new pattern needing its own validation.
- **Partition-filtered reads.** All three of the operator's reads against its own new partitioned
  tables carry the matching partition predicate (`DATE(built_at)=target_snapshot_date` /
  `DATE(detected_at)=target_snapshot_date`). Reads inside the DDL 103 procedure against
  `export_archive` and `sap_mirror_doc` carry no partition filter, but this matches how every
  other procedure in this project reads those two tables (pre-existing, not introduced here) —
  flagging as a note, not a new gap this artifact is responsible for closing.
- **Zero-row build.** If `_events` is empty, `_ready` and `_hold` are both empty, the population
  ASSERT holds trivially (0=0+0), and the manifest still records the (empty) run — correct
  behavior for a month with no ONETIME activity, not an error path.

## Required note — the checker crashes on every invocation; not a hypothetical gap

The evidence disclosed the checker "was not run live because the local GCP tool account returned
its usage limit." I ran it myself:

```
powershell -File scripts\check_v3_delivery_control_plane.ps1
→ ERROR: (gcloud.workflows) Invalid choice: 'get-iam-policy'.
```

`gcloud workflows get-iam-policy` (added in this exact delta, `90e6fd5`, to populate
`$workflowPolicy` for the broad-Invoker-rejection check) **does not exist** — confirmed via
`gcloud workflows --help`, which lists no IAM/policy subcommand at all. Every other `gcloud` call
in the script (`storage buckets get-iam-policy`, `iam roles list`, `projects get-iam-policy`,
`run services get-iam-policy`) is valid — I re-ran each individually and they all work — but this
one line means the script throws and terminates before producing *any* JSON output, every time,
regardless of live state. The "machine gate" cannot currently gate anything.

This does not block the runbook itself: the actual administrator commands in
`V3_DELIVERY_CONTROL_PLANE.md` never attempt a workflow-resource-level IAM policy read or write —
the trigger's custom-role binding is granted entirely at the *project* level
(`gcloud projects add-iam-policy-binding`), which the checker's `$projectPolicy` variable (a valid
call) already covers. The fix is almost certainly to delete the `$workflowPolicy` fetch and drop it
from the `$broadTriggerBindings` search, relying on `$projectPolicy` alone — but this needs its own
delta and re-review, not a guess applied here.

## Checked — the runbook's own commands (independent of the broken checker)

- **Minimal-sufficiency of the three bucket bindings**: traced the promoter's actual GCS calls
  (reviewed in RQ-2136) — `source.reload()`/hash needs archive `objectViewer`;
  `destination.rewrite(..., if_generation_match=0)` needs production `objectCreator`;
  `destination.reload()` (to read back generation/size/CRC32C before returning evidence) needs
  production `objectViewer`. The three conditional bindings in Phase A are exactly this set — no
  more, no less. The `2cfcffc` delta correctly added the previously-missing production `objectViewer`
  grant (without it, the promoter's own destination-reload step would have failed with a
  permission error on every real invocation).
- **Custom-role scoping and broad-Invoker rejection (intent, not the broken execution)**:
  `nightlyWorkflowCreator` is created with exactly `workflows.executions.create` at `--stage=GA`,
  matching what the checker's (valid) `$triggerRoleSummary` check requires. The explicit
  instruction "Do not substitute a broad runtime identity" and the checker's intent to reject a
  predefined `roles/workflows.invoker` grant are consistent with the same pattern already reviewed
  and confirmed correct in RQ-2044/RQ-2107's dispatcher-side custom roles this session.
- **Scheduler create→pause→update race safety**: the placeholder schedule (`0 0 1 1 *`, Jan 1) is
  genuinely dormant relative to any plausible deployment date, matching the same safe pattern
  already verified (by actually triggering the equivalent race-guard) in the post-import admin
  runbook reviewed earlier this session.
- **Nested execution argument shape**: `$argument = @{...} | ConvertTo-Json -Compress` then
  `$messageBody = @{ argument = $argument } | ConvertTo-Json -Compress` produces a JSON object whose
  `argument` field is itself a JSON-encoded *string* — this matches the Workflows Executions API's
  documented contract (`argument` is a string field, not a nested object) and the checker's
  `ConvertFrom-Base64Json` → `[string]$schedulerBody.argument | ConvertFrom-Json` correctly reverses
  that exact double-encoding.
- **Workflow service-account normalization**: `.Replace('projects/-/serviceAccounts/', '')` matches
  the actual return shape of `gcloud workflows describe --format=json`'s `serviceAccount` field —
  confirmed by comparing against the same field I've read directly from live `workflows describe`
  output earlier this session.
- **PowerShell 5.1 compatibility**: no ternary, null-coalescing, or pipeline-chain operators
  anywhere in the file; `Set-StrictMode -Version Latest` at the top. The script *did* parse and
  begin executing correctly — the failure was a runtime `gcloud` error, not a PowerShell syntax
  error.
- **No command in the checker mutates state**: every call is `describe`/`list`/`get-iam-policy`
  (read-only) — the one broken call is also a read attempt, not a mutation; it just targets a
  non-existent subcommand.
- **Rollback and production gates**: pause-trigger-first, restore-prior-revision,
  never-delete-evidence rollback instructions and the six ordered separate production gates are
  consistent with every other admin runbook reviewed this session.

## Verdict

PASS WITH REQUIRED NOTE. The deployment runbook's own commands are sound, minimally scoped, and
consistent with every previously-reviewed sibling runbook this session. The machine checker has a
confirmed, fatal bug (a nonexistent `gcloud` subcommand) that must be fixed and re-reviewed before
an administrator can rely on it as the control-plane readiness gate — I found this by actually
running the script, closing exactly the gap the commit's own evidence disclosed it couldn't test.
No deploy, IAM, scheduler, GCS, workflow execution, or SAP action was performed by me in this
review — I only ran the checker (which itself performs no mutation) and individually re-verified
each `gcloud` subcommand it calls.

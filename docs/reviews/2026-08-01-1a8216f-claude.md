## The five requested checks

1. **Selector equivalence:** both files now order `UpdateDate DESC, UpdateTime DESC,
   SHA256(TO_JSON_STRING(raw_doc)) DESC` over the same 59-field payload. Hash-input equality
   verified structurally: 043's `raw_delta` takes its field names from its first branch, which
   matches 024's alias list exactly (the 59/59 check from the earlier review), and both apply the
   same transforms (SAFE_CAST floats, FORMAT_DATE strings, `DATE(UpdateDate)`), so identical source
   rows serialize to identical JSON → identical hash → identical winner. The one structural
   difference (024 branches use `SELECT DISTINCT`, 043's delta doesn't) is immaterial under a
   content hash: exact duplicates share a hash and any pick among them is the same row.
2. **Hash placement:** third key, strictly after both recency keys — it only resolves residual
   ties, never overrides recency. The old `DocEntry DESC` term (constant within `PARTITION BY
   DocEntry`, i.e. provably inert) is correctly deleted rather than left as dead code.
3. **Alias scope:** the union subquery is named `AS raw_doc` and projected as `raw_doc.*`;
   `TO_JSON_STRING(raw_doc)` therefore serializes exactly the transformed mirror row and cannot
   see `_rn`. Valid in both contexts — confirmed by the statement-level typed-literal dry-run gate
   (both extracted selectors validate with identical true semantic estimates of 7,319,841,706
   bytes; 0 bytes billed).
4. **NULL/float JSON stability:** `TO_JSON_STRING` is deterministic per value (NULL→null, floats
   render identically for identical doubles, both paths produce the same doubles via the same
   casts); `SHA256` yields BYTES with a total order under DESC. Distinct payloads cannot collide in
   practice; identical payloads tie harmlessly.
5. **8,538 vs 5,566 distinction:** correctly framed — 8,538 is the measured population *capable* of
   flipping (conflicting payloads at max recency; 5,936 within-source + 2,602 cross-source, sums
   check), 5,566 was one run's *observed* flips, a subset as expected. The extra diagnostic that
   the incremental mirror holds zero below-maximum-recency rows properly eliminated the
   old-recency-pick alternative before this fix was written. Diagnostics carry full job provenance.

## Notes (non-blocking)

1. **Deterministic ≠ business-chosen.** For the 8,538 keys — especially the 2,602 cross-source
   ties — the hash picks a stable but semantically arbitrary winner. That is strictly better than
   the previous unstable-arbitrary behavior and unblocks the gate, but if Boat/Aware ever want a
   preference (e.g., current `SAP_LIVE` over historical shards), a source-priority key belongs
   *between* recency and the hash. Decision-when-needed, not now.
2. **Binding next steps before repoint** (unchanged from the chain-③ review): redeploy both →
   re-run the exact row-for-row gate (expected 0/0) → measure the 025-level delta on the flipped
   keys (how many change status/InvoiceNo at (OrderItem, Period) grain) and report it — do not
   assume nil.
3. Chain-② note: 024 as deployed will now differ from any pre-tiebreak mirror rebuild on ≤8,538
   keys; the chain-② refresh verification should quote this bound rather than expecting a
   zero-delta rebuild.

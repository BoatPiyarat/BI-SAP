## 2. ASSERT audit

- **Posted path (POSTED_CORRECT/POSTED_WRONG): no bypass.** All six evidence elements required in
  one conjunction; a NULL anywhere makes the ASSERT condition NULL, and BigQuery ASSERT passes only
  on TRUE — fail-closed confirmed (including NULL `import_outcome`).
- **REJECTED_NEVER_POSTED: no bypass** of the stated contract (DocEntry strictly NULL, JE
  NULL-or-empty, LogID + `REJECTED` + evidence required). **NOTE 2:** `sap_status` is unconstrained
  on this path — a never-posted record can carry `sap_status='Paid'`; add `AND (p_sap_status IS
  NULL OR TRIM(p_sap_status)='')` for symmetry.
- **NOT_FOUND / INCONCLUSIVE:** base requirements (verifier, evidence_timestamp, source_uri) apply
  — nothing *claimed* is skipped. **NOTE 1 (pre-deploy):** NOT_FOUND currently accepts a non-NULL
  `sap_doc_entry`/JE/`import_outcome='SUCCESS'` — a self-contradictory record ("not found, here is
  its DocEntry") would insert cleanly and poison exactly the FA-facing counts this register exists
  for. Add: `ASSERT p_decision != 'NOT_FOUND' OR (p_sap_doc_entry IS NULL AND (p_je_reference IS
  NULL OR TRIM(p_je_reference)=''))`. INCONCLUSIVE legitimately carries partial evidence — leave
  free, but say so in the header.
- **verification_id uniqueness / append-only:** repo-wide scan found **zero**
  UPDATE/DELETE/MERGE/TRUNCATE statements touching `sap_fa_verification`; 042 is the table's only
  reference — append-only holds in source. **NOTE 3:** the `ASSERT NOT EXISTS … INSERT` pair is not
  race-proof (no lock between check and insert; two concurrent CALLs with the same id could both
  land). Acceptable for human-paced evidence entry; cheap backstop is a scheduled uniqueness audit
  (`HAVING COUNT(*)>1`) rather than procedure changes. BigQuery cannot block ad-hoc DML by a
  privileged human — that remains an IAM matter, not a 042 defect.

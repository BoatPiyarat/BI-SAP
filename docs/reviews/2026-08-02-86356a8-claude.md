# Review — 86356a8 (cancel-old Paid/Pending status gate + RULE-21/22 interpretation correction)

**Queue entry:** RQ-20260802-cancel-old-status-gate · **Class:** A · **Reviewer:** Claude Code
**Verdict:** **PASS WITH NOTES** — the literal reading is correct and the gate is implemented
cleanly; two boundary gaps to close, one of which answers Boat's explicit question.

## The three requested checks

1. **CASE precedence — correct.** `HOLD_OLD_NOT_PAID_OR_PENDING` sits after `HOLD_OLD_NOT_IN_SAP`
   and `HOLD_OLD_ALREADY_TERMINAL`: terminal rows are a subset of non-Paid/Pending, so the more
   specific label wins first and the new gate catches the residual states — right ordering.
2. **NULL handling — the trap was dodged explicitly.** `TransactionStatus NOT IN (...) OR
   TransactionStatus IS NULL`: without the OR-IS-NULL, a NULL status would evaluate the NOT IN to
   NULL and silently escape the count. Handled.
3. **The 92 are non-citable until rerun** — stated in both the finding and the design; the prior
   run is retained as provenance.

## The interpretation correction — Boat's literal reading is right, and the reversal was safe

Rule 21's "a Paid document must be accepted before **its own** Cancelled document is eligible"
refers to the old document's own lifecycle, not the replacement's. The previous interpretation
(replacement Paid ACK gating cancel), which this reviewer PASSed in `a52b495`, was **stricter than
intended** — over-constrained, fail-closed, incapable of releasing anything unsafe — and the rule
owner has now corrected it. Disclosure recorded; no rework resulted (nothing was built on the
stricter reading, and the mapping diagnostic it motivated remains fully valid for the credit-shell
stage, where the design now correctly re-homes it).

## NOTE 1 (close with next revision): the target Cancelled literal vanished from the track doc

The pre-edit design said "change only TransactionStatus to Cancelled or Cancelled (Change order)";
the edited step 4 says "change only TransactionStatus" with no value. For THIS track the literal
must be pinned: **`Cancelled (Change order / Rejected)`** (rules 18/20; 025 layer-1 recognizes it).
Leaving it unspecified re-opens a literal-invention risk at payload time — the exact class rule 28
prohibits for payment fields.

## NOTE 2 (Boat's question): plain cancellation vs CancelChange — separated by construction, but the boundary is undocumented

Verified: this track's population is **only** `cancelled_change_orders` links, so ordinary
cancellations (cancelled outright, no replacement, no credit-shell) are excluded *structurally* —
they cannot enter this preflight. But no document says so, and nothing defines where plain-cancel
logic will live. Required boundary statement + future track skeleton:
- **Plain-cancel track (separate):** population = cancelled items *without* a change-order link
  (e.g., `is_cancelled_effective` minus `cancelled_change_orders` membership); same SAP gates
  (presence, Paid/Pending, full spine, immutable InvoiceNo, clone-56-change-status-only) but
  target literal **`Cancelled`**, **no item mapping, no credit-shell stage, no replacement
  semantics**; legacy cancel views (`process_2_cancel_new`, RCL cancel) are pre-RULE-21/22 and are
  not a readiness basis for it either.
- One sentence in each design doc forbidding cross-routing: a linked pair never goes through the
  plain-cancel track, and an unlinked cancel never enters the credit-shell state machine.

## NOTE 3 (minor): the status gate accepts `'Paid','paid','Pending'` — if a lowercase `'pending'`
exists anywhere in the mirror it would be held as non-cancellable (fail-closed, so acceptable);
have the rerun report the distinct status inventory once so the literal set is evidence-based.

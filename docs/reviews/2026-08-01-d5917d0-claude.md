## The eight requested checks

1. **Duplicate-trigger prevention — sound.** >1 bronze object → hard stop at three separate points
   (pre-extract, post-extract, during the wait loop); exactly-1 → extract skipped; loader triggered
   at most once; timeout → throw with an explicit do-not-retrigger instruction. A post-timeout
   re-run degrades safely: it skips extract (1 object) and retries the loader once — a sane manual
   recovery loop, not an amplification path.
2. **Native-command error handling — correct pattern.** `$ErrorActionPreference='Stop'` +
   StrictMode + every native call routed through `Invoke-Checked`'s `$LASTEXITCODE` test (native
   commands never throw on their own — this is the right guard). `gsutil ls` tolerates only exit
   0/1 (1 = empty match), anything else throws. No failure shape found that silently continues:
   the only two continue paths are the legitimately healthy ones (skip-extract; healthy-zero-row
   extract → skip loader, which matches the §3.6 zero-row disambiguation because a login failure
   exits nonzero from `--wait` and stops the script).
3. **Signatures/order vs live — exact.** The ten steps match the live post-047 body in content and
   order, including run_scope args on the two mirror procedures (see NOTE 1) and no-arg calls
   elsewhere.
4. **Dry-run/cost guards — present and per-step.** Each CALL is its own job with its own 20 GiB
   cap and unique timestamped job ID (which doubles as double-submit protection — BigQuery rejects
   reused job IDs).
5. **Timeout behavior — fail-closed**, and the loop also aborts if a second object appears mid-wait.
6. **Silent-continue audit — none found** (see 2).
7. **Recovery evidence — arithmetic all verified.** Cap math exact: 21,474,836,480 −
   20,246,650,795 = 1,228,185,685 ≈ 1.14 GiB, and standalone validation at 18,168,069,896 bytes
   proves the wrapper CALL could never fit (early steps + 18.2 GB > 20 GiB) — the per-step design
   is mandatory, not stylistic. Recovery correctly resumed at the failure point
   (validation/delta/status only), no blind rerun. Post-recovery counts reconcile:
   `sap_mirror_doc` 1,662,648 + 2,241 (extract `sw95z` rows) = **1,664,889 exact** — first
   production proof of the incremental MERGE arithmetic; downstream 290,319 consistent across
   expected_state/delta_export/daily_status.
8. **No interface writes — confirmed from the script text**: bronze listing is read-only; no
   `gsutil cp/rsync`, no `EXPORT DATA`, no `gs://interface-file/**` reference.

## Notes (non-blocking)

1. **`'MANUAL:operator'` will be logged as `NIGHTLY`** in `pipeline_run_log`: the procedures
   classify `run_type` via `STARTS_WITH(run_scope, 'ADHOC:')`. Change the two args to
   `'ADHOC:manual-operator'` so manual runs don't masquerade as scheduled ones in the audit trail.
   One-line change, worth doing before first use.
2. **Schedule-collision window** — tonight's own evidence demonstrates it: the 21:00 scheduled V3
   ran before the loader finished and was stale for the batch. The script cannot guard the
   *scheduled* jobs; add one runbook line: avoid running across the 20:30 extract / ~21:00 V3 /
   loader window (or accept that a stale scheduled pass self-corrects on the next run, as it did
   here).

Also noting for the record: the runbook's execution evidence contains the first operational data
from the post-047 nightly (scheduled V3 ran 14:00:01–14:05:01Z without error) — the full
first-night verification remains tomorrow's scheduled run against a fresh batch, per RQ-2000.

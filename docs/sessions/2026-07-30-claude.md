## Priority 4 — `bq_safe_query.sh` fixed per BLOCK `docs/reviews/2026-07-30-a56f6d1-codex.md`

Both substantive BLOCK findings fixed directly in `scripts/bq_safe_query.sh`:

1. **Fail-open parser → fail-closed.** Extracted the byte-parsing logic into a single
   `parse_bytes_processed()` function. Previously, `jq -r '(...) // "0"'` treated **any** absent or
   unparseable path as `0` bytes, silently letting the real query run with zero cost check. Now:
   absent/missing field, jq failure, and non-numeric values are all a hard error (exit 3, real query
   never runs); only a JSON-explicit `"0"` is treated as a real zero-byte estimate. The no-`jq`
   fallback was fixed the same way.
2. **`--force` resolved by removal, not by raising the real cap.** The old code advertised that
   `--force` would let an over-threshold query run, but still capped `--maximum_bytes_billed` at 20
   GiB regardless — the flag could never do what it claimed. Chose the simpler, safer of the two
   options Boat offered: **removed `--force` entirely; 20 GiB is now a hard ceiling with no
   override.** A query estimated above it is never run by this script — the fix is to redesign the
   query (partition filter, narrower date range, `TABLESAMPLE`), not to force it through. Confirmed
   `--force` is no longer silently accepted: passing it now falls through to the positional-SQL slot
   and errors loudly (`unexpected extra argument`) rather than being swallowed.
3. **Added `--self-test`** — 7 offline parser cases, no BigQuery calls: current JSON shape, nested
   JSON shape, explicit zero, missing field, malformed value, threshold-equality value, threshold+1
   value. Ran it twice — once with `jq` on `PATH`, once with `PATH` restricted to hide `jq` (exercises
   the grep fallback) — **7/7 passed both times**:
```
PASS: current JSON shape
PASS: nested JSON shape
PASS: explicit zero
PASS: missing field
PASS: malformed value
PASS: threshold equality value parses
PASS: threshold+1 value parses

SELF-TEST: 7/7 passed
```
   Also smoke-tested the live path end-to-end with a trivial real query (`SELECT 1 AS x`) — dry-run
   correctly reported `0 bytes`, real run executed and returned `1`, confirming the explicit-zero
   fix works through the actual `bq` call, not just the offline harness.

## Priority 5 — `sap_mirror_doc` MERGE design (`sql/ddl/043`), source only, not deployed

Designed `sp_refresh_sap_mirror_doc_incremental` — replaces `024`'s full `CREATE OR REPLACE TABLE`
(rescans all 4 source tables every run) with a watermark-filtered `MERGE`. Full detail and rationale
in the file's own header comments; summary here.

**Spec followed exactly**: `UpdateDate`/`UpdateTime` are now selected (fixing the gap found in
Priority 1) and inserted into the per-DocEntry tiebreak as `BatchRunDate DESC, UpdateDate DESC,
UpdateTime DESC, DocEntry DESC`. New `sap_mirror_doc_watermark` singleton control table tracks
`(last_upd_date, last_upd_time)` actually merged, so the next run's source filter is
`UpdateDate > wm_date OR (UpdateDate = wm_date AND UpdateTime > wm_time)`. `SAP_LIVE` itself is
untouched — no clean/dedupe/truncate/rebuild/delete anywhere in this file, reaffirmed in its header.

**⚠️ Cost-win caveat, flagged rather than oversold**: checked `SAP_LIVE`'s metadata directly —
**no partitioning, no clustering at all**. BigQuery's columnar engine reads the full value of every
referenced column across the whole table regardless of a `WHERE UpdateDate > watermark` filter;
there's no block-pruning to skip old rows. The "~100x" cost win cited in
`docs/knowledge/KNOWLEDGE_ADDENDUM_20260730_v3.md` §C6.4 is more accurately attributed to
*downstream consumers* reading the already-deduplicated, clustered `sap_mirror_doc` instead of
scanning `SAP_LIVE` directly — a win that already exists today regardless of this file. What this
design actually buys: the UpdateTime correctness fix, less downstream dedup/`ROW_NUMBER` compute
(only the delta needs re-ranking), and less write cost (`MERGE` touches only changed DocEntries, not
a full table rewrite). It does **not** cut `SAP_LIVE`-side scan bytes anywhere near 100x on its own
— if that scan cost needs fixing directly, the real lever is adding `CLUSTER BY` to `SAP_LIVE`
itself (a schema change, not a data cleanup — arguably compatible with the append-only hold since it
touches no rows — but that's a separate decision, not assumed here).

**Verification done**: dry-ran the full file (`bq query --dry_run` over the whole script) —
validated clean, `0 bytes` (procedures/DDL don't carry a per-run scan estimate the way a `SELECT`
does; this confirms syntax only, not runtime cost). Not executed. Cutover plan (bootstrap full run →
row-for-row diff against `024`'s output → only then repoint the nightly chain) is written into the
file's own trailing comment, not run.

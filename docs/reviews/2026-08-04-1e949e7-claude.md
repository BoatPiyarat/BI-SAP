## Required Note 1 — Gmail search never excludes already-ingested messages

`findCandidates_`'s query (line 66) is
`label:"notification SAP upload" from:... subject:"[LIVE]" newer_than:1h` — it never adds
`-label:"ingested"`. `INGESTED_LABEL` is applied to the *thread*, but the search still matches on
the original `"notification SAP upload"` label alone, which is never removed. Concretely: a message
successfully ingested on poll cycle N will be rediscovered as a "candidate" on every subsequent
poll cycle (documented as 15-minute) until it ages out of the 60-minute lookback — roughly 3–4 extra
reprocessing cycles per message.

This is not a data-safety bug — every downstream write is idempotent (GCS 412-tolerant create-only,
BigQuery MERGE-by-key) — but it is real waste (Gmail/BigQuery/GCS/UrlFetch calls repeated for no
reason) and it removes a layer of protection from the ambiguity check: `pollSapResultMailbox` only
verifies `logIds.length !== 1` (line 34) within a manifest group; it never checks `group.length`.
If two distinct candidate objects for the *same* `logId` ever land in one group — which becomes far
more likely once the same message is routinely rediscovered every cycle — `logIds` still has length
1, the check passes, and `group[0]` is silently processed while `group[1]` is silently dropped with
no error, no log, nothing. In the common case (one real message, repeatedly rediscovered) this just
means redundant reprocessing; in the rarer case of a genuine second message carrying the identical
`logId` (e.g., a forwarded copy or resend), the second one is dropped without trace.

**Fix required before deploy:** add `-label:"ingested"` to the search query, and additionally guard
`group.length !== 1` alongside the existing `logIds.length !== 1` check so a same-`logId` duplicate
candidate set fails closed instead of silently dropping one.

## Required Note 2 — OAuth scope broader than the commit's own stated requirement

`sap_result_ingestion.appsscript.json` declares `https://www.googleapis.com/auth/cloud-platform` —
this grants the script principal access to essentially every GCP API and resource in the project,
not just BigQuery and this one GCS bucket. `SAP_RESULT_INGESTION_DEPLOYMENT.md`, added in this same
commit, explicitly asks for "narrowly scoped Gmail, BigQuery, and `gs://rcb-bronze-zone/...` access"
— the scope declaration contradicts its own deployment doc. Apps Script supports declaring the
narrower `https://www.googleapis.com/auth/bigquery` and
`https://www.googleapis.com/auth/devstorage.read_write` scopes directly (both are used only via
`UrlFetchApp` + `ScriptApp.getOAuthToken()`, not an Advanced Service, so nothing here depends on
`cloud-platform` specifically).

**Fix required before deploy:** replace `cloud-platform` with the narrower `bigquery` and
`devstorage.read_write` scopes.

## Non-blocking observations

1. On the `FAILED` path (line 45), `writeHeartbeat_` is called with a hardcoded `0` instead of the
   `processed` count (line 29/39) accumulated before the failure. If manifest group 1 of 3 succeeds
   and group 2 throws, the heartbeat reports `last_message_count=0` even though one manifest's data
   is already correctly committed — misleading for on-call triage, not a data-correctness issue
   (the committed BigQuery/GCS writes from the successful iterations are unaffected).
2. The header comment claims `POLL_MINUTES (default 15)` as an optional Script Property, but no
   code reads `POLL_MINUTES` anywhere — confirmed by grep. The real poll cadence comes entirely from
   the externally-installed Apps Script time trigger described in the deployment doc. Harmless, but
   the comment should either be removed or the property should actually be wired to something (e.g.
   validated against the installed trigger interval).
3. `query_`'s BigQuery REST call checks `result.jobComplete` and throws if false, without polling
   `jobs.getQueryResults` to wait out a slow job past the synchronous request's default wait. Given
   every query here is a small single/few-row lookup or keyed upsert, this is low risk, but there's
   no fallback if BigQuery is transiently slow.

## Observation (not a required note)

The cross-manifest-reuse check is a `SELECT`-based precondition evaluated *before* the transaction,
not enforced inside the same atomic `MERGE` (e.g. via a `WHEN MATCHED AND t.export_run_id !=
s.export_run_id THEN ERROR` clause). In the narrow case of two genuinely concurrent first-time
enqueue calls for the same brand-new `log_id` with *different* `export_run_id`/`sap_file_name`, both
could observe "no existing row" at their pre-check, and whichever `MERGE` commits second would see
`log_id` already matched and simply no-op (0 rows, no error) rather than raising the clear
"already bound to a different delivery manifest" assertion a sequential retry would get. This does
not corrupt data — at most one manifest ever binds to the `log_id` — but the caller of the losing
request gets a silent success instead of the informative rejection the claim describes. Given the
intended usage (one enqueue call per `log_id`, from a single SAP-result ingestion pipeline
execution, not a naturally concurrent multi-caller path), this is a theoretical edge rather than a
live gap, so it doesn't block this review — flagging for awareness if the calling pattern ever
becomes genuinely concurrent.

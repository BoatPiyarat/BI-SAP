Checked: (1) incident arithmetic: 733,596 − 61,133 = 672,463 duplicate rows ✓, zero bad records
consistent with `b00af18`'s job table. (2) The "outer status ≠ inner side-effect" failure-semantics
section is the right generalization and cites the two prior project lessons accurately. (3) Guard 2
is honest where it matters: `maxDeliveryAttempts=5` is documented as approximate/best-effort
containment (~5 duplicate commits still possible), **not** one-attempt semantics — correctness is
correctly assigned to 043's idempotent MERGE (currently BLOCK, fixes proposed in

JOBS_BY_PROJECT limitation (no `outputRows` in the view; per-job statistics needed for diagnostics)
is stated so the guard isn't oversold.

NOTE 1 — Guard 1 threshold vs the chunking fix: "alert when successful LOAD jobs exceed one" is
correct only while extraction writes exactly one object per run. Permanent-remediation item 2 makes
the extractor split into bounded chunks — after that, N chunks → N legitimate LOAD jobs and Guard 1
as written alerts every night. The guard should compare LOAD-job count against the extract's
reported chunk count (already logged as `success: N chunks`), not against the constant 1.

NOTE 2 — ack-deadline interaction worth one line in the design: with a 10s ack deadline and a
loader that runs minutes, every run relies on deadline extension; if the DLQ is added, a slow but
healthy run that fails extension could dead-letter a *good* file. The DLQ alert runbook should
include "check whether the object was actually loaded before replaying it."

## Verification 2 — independently re-ran the reconciliation query

Rather than trust the recorded byte count and identity count alone, re-derived the check directly
against live BigQuery (own query, own job, not the original):

```sql
WITH run_identities AS (
  SELECT DISTINCT order_item, period, charge_id, delivery_status
  FROM `pacific-plating-282708.sap_integration_v3.export_archive`
  WHERE export_run_id = 'V3DAILY-20260803-113257-55042e7c'
),
mirror_match AS (
  SELECT ri.order_item, ri.period, ri.charge_id, ri.delivery_status,
    m.TransactionStatus AS mirror_status
  FROM run_identities ri
  LEFT JOIN `pacific-plating-282708.sap_integration_v3.sap_mirror_state` m
    ON m.U_OrderItem = ri.order_item AND m.U_Period = ri.period
)
SELECT
  COUNT(*) AS n_identities,
  COUNTIF(delivery_status = 'DELIVERED') AS n_delivered,
  COUNTIF(mirror_status IS NULL) AS n_missing_from_mirror,
  COUNTIF(mirror_status = 'Paid') AS n_mirror_paid,
  COUNTIF(mirror_status IS NOT NULL AND mirror_status != 'Paid') AS n_mirror_other_status,
  COUNT(DISTINCT mirror_status) AS distinct_mirror_statuses
FROM mirror_match
```

Dry-run 42,001,973 bytes; real run same. Result: `n_identities=558`, `n_delivered=558`,
`n_missing_from_mirror=0`, `n_mirror_paid=558`, `n_mirror_other_status=0`,
`distinct_mirror_statuses=1`. Matches the commit's claim exactly (own byte estimate differs from
the recorded 73,208,397 bytes — expected, different query shape/join order, not a discrepancy).

## Blocking findings

1. The deterministic BigQuery `jobId` is `${run_id + "-" + step}` while `run_id` contains an RFC
   timestamp with `:`. BigQuery job IDs permit only letters, digits, `_`, and `-`; both mirror jobs
   therefore fail at insertion. Sanitize/generate a separate valid BQ job ID and retain run_id as
   a label/log field. Source:
   https://cloud.google.com/bigquery/docs/reference/rest/v2/JobReference
2. On deadline the workflow calls `jobs.cancel`, performs one immediate `jobs.get`, then raises
   regardless of whether state remains RUNNING. Google states cancellation returns immediately and
   clients must poll status. This does not “verify cancellation reached terminal” and leaves the
   original overlap/replay risk open. Poll to DONE, gate terminal `errorResult`, and only then
   return a safely failed terminal outcome. Source:
   https://cloud.google.com/workflows/docs/reference/googleapis/bigquery/v2/jobs/cancel

Pre-deploy pinning of the actual control-object path/schema remains a hard gate, not a PASS claim.

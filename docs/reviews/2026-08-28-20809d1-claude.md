## Required questions, answered directly

**1. Does removing `NOT NULL` from the ARRAY field follow BigQuery storage semantics without
weakening the whole-item hold contract?**
Yes. BigQuery does not support a `NOT NULL` constraint on an `ARRAY<...>` column — array-typed
columns are represented as an array container (empty when there are no elements) rather than as a
nullable scalar, so `NOT NULL` on the array type itself is a category error, not a stricter
constraint. The corrected declaration, `invalid_fields ARRAY<STRING>` (no `NOT NULL`), is the only
form BigQuery accepts. Read the population query directly:

```sql
FROM _candidate c,
UNNEST(REGEXP_EXTRACT_ALL(TO_JSON_STRING(c),r'"([^"]+)":(?:null|"NULL")')) field_name
...
GROUP BY c.OrderItem;
```

This is a correlated `CROSS JOIN UNNEST(...)` with no `LEFT`/`OUTER` modifier. Under BigQuery
correlated-UNNEST semantics, a source row whose `REGEXP_EXTRACT_ALL(...)` result is an empty array
produces **zero** output rows for that source row (inner-join behavior), so an `OrderItem` only
appears in `_candidate_required_hold` at all when at least one field matched, and `ARRAY_AGG` over
that non-empty match set can never be empty or NULL. So the schema-level nullability is a syntax
formality only — every row that is actually written to the hold table carries a genuinely populated
`invalid_fields` array, and the whole-item quarantine contract (which fields, on which item) is
unweakened.

**2. Does the durable ledger remain sufficient and PII-safe with a nullable schema declaration that
is always populated by `ARRAY_AGG`?**
Yes, per the same analysis as Q1. The regex capture group (`"([^"]+)"` immediately preceding a
literal JSON `null` or the string `"NULL"`) can only ever capture the JSON *key* name, never a data
*value* — this was already established as PII-safe in the `2026-08-27-37b5a9b-claude.md` review and
this delta does not touch that regex or the capture logic, only the column's nullability keyword.
The "always produced by `ARRAY_AGG`" claim in the request is correct and independently confirmed
above from the join semantics, not merely asserted.

**3. Does the checker genuinely prevent reintroduction of unsupported ARRAY `NOT NULL` syntax?**
Partially — with a scope caveat worth naming. Two independent guards exist in
`scripts/check_v3_unit5_required_hold_fix.py`:
- a required positive token `"invalid_fields ARRAY<STRING>,invalid_period_rows INT64 NOT NULL"`
  (exact substring, matching the corrected DDL's actual formatting with no space/keyword between
  `ARRAY<STRING>` and the following comma);
- an explicit negative check, `if "invalid_fields ARRAY<STRING> NOT NULL" in ddl: raise SystemExit(...)`.

Both are **literal-string** matches, not a general regex over `ARRAY<[^>]+>\s+NOT NULL`. Verified
against the historical `37b5a9b` text (via the `--git-ref` self-test cited in the request as RED)
and the current corrected text (PASS): the guard correctly detects *this exact* regression pattern
for *this exact* column. It would **not** catch a differently-formatted reintroduction (extra
whitespace/newline before `NOT NULL`) or a *new* array column elsewhere in the file declared with
`NOT NULL`. This is a real but narrow gap: worst case on a future regression is another failed
BigQuery dry-run/validation cycle (fail-closed, as already demonstrated by this incident), not a
silent production defect, since BigQuery itself rejects the syntax at validation time regardless of
whether the local checker catches it first. Non-blocking; flagged as a note.

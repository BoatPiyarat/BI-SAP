### The 297,413 / 297,604 (+191) dedup-loss claim — could not reproduce; independent test run instead

Reasoned through the only mechanism that could plausibly produce a count difference of this shape:
`sap_mirror_state`'s picking rule (`sql/ddl/025_sap_mirror_state.sql`) ranks candidate documents per
`(OrderItem, Period)` key by status → has-invoice → `BatchRunDate` (day-grain only) DESC → `DocEntry`
DESC as the final tiebreak — and neither `sap_mirror_doc` nor `sap_mirror_state` currently carries
`UpdateDate`/`UpdateTime` at all (confirmed by reading both DDL files in full — not in either
`SELECT` list). If two candidate documents for the same key share a `BatchRunDate` day, `DocEntry`
DESC assumes higher DocEntry = more recently updated, which is not guaranteed.

Tested this directly. Query timestamp: **2026-07-30T15:13–15:14 UTC**. Built a
`DocEntry → MAX(UpdateDate, UpdateTime)` lookup from the same 4 source tables `sap_mirror_doc`
unions, joined it to `sap_mirror_doc`'s own candidate rows, and re-ran `025`'s exact `ROW_NUMBER()`
twice — once as currently coded, once with `upd_date DESC, upd_time DESC` inserted before the final
`DocEntry DESC` tiebreak (dry-run 349,412,865 bytes; real run same):

```
ambiguous_keys = 330,288
keys_where_pick_changes = 0
```

**Zero keys changed their winning document** when the tiebreak was corrected to use real
chronological order instead of `DocEntry DESC` alone, against the *current* data snapshot. I cannot
corroborate the specific `+191` figure — either the original analysis tested a different population/
grain than I reconstructed here, or the underlying data has shifted since (`SAP_LIVE` keeps growing
nightly per the open bloat incident, so a same-day ambiguity present at 14:27:28 UTC could plausibly

**This does not change Priority 5's recommendation**: including `UpdateDate`/`UpdateTime` before

protects against a real same-day multi-update ambiguity on a future date where it would matter. See
Priority 5 below for the actual MERGE design.

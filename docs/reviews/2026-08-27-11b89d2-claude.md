## Focus areas from the request, answered directly

**1. Does the runner truly gate exact revision, source identity, delivery-false, workflow
concurrency, active SAP extraction, bronze ownership, both Scheduler prestates, and the legacy
20:30 overlap window before execution?** Yes, traced each:

- **Revision + source identity + delivery-false + concurrency**: all four live inside
  `build_v3_common_execution_census.ps1`, called first in the runner (`if (-not
  $census.verification_passed) { throw ... }`). `$verificationPassed` is a single AND of:
  `revisionId -eq $ExpectedRevision`, `state -eq 'ACTIVE'`, exact service account match,
  `$sourceIdentityPassed` (character-length-equal AND every character equal, except the narrow
  comment-only em-dash carve-out — Note 1), `$deliveryFalse` (regex-matched `delivery_enabled:
  false` literally present) AND NOT `$deliveryTrue`, AND zero ACTIVE+QUEUED executions. Any one
  failing flips the whole AND to false, and the script `exit 1`s.
- **Active SAP extraction**: `$activeExtractExecutions` filters `sap-extract-job` executions for
  `-not $_.status.completionTime` (i.e., still running); nonzero throws.
- **Bronze ownership**: `gcloud storage objects list gs://rcb-bronze-zone/SAP/production_database/**
  --limit=1`; nonzero throws "refusing to take ownership of an existing batch."
- **Both Scheduler prestates**: exact `state`/`schedule`/`timeZone` equality checks against both
  `v3-nightly-orchestrator` (must be `PAUSED`) and `sap-extract-schedule` (must be `ENABLED`), both
  at the identical `30 20 * * *` / `Asia/Bangkok` cron — matching the live state this project's
  session notes have established throughout today.
- **Legacy 20:30 overlap window**: `$minuteOfDay -ge 1170 -and $minuteOfDay -lt 1320` blocks
  19:30–21:59 ICT inclusive of a buffer either side of the legacy 20:30 run, computed from
  `TimeZoneInfo` conversion with an `SE Asia Standard Time`→`Asia/Bangkok` fallback for
  cross-platform correctness.

All seven gates run and must pass, in this order, before the BigQuery preflight (`bq_safe_query.sh
-f $preflightSql`) is even invoked, and the preflight itself must also pass before `$PreflightOnly`
returns or the real `gcloud workflows run` executes.

**2. Can the flags invoke only the normal delivery-disabled path and not queue silently?** Yes.
`delivery_enabled: false` in `infra/v3_nightly_orchestrator.workflows.yaml` (line 55) is an
unconditional literal assignment — unlike `promotion_service_url` and
`permission_rehearsal_only`, which explicitly read `default(map.get(args, "..."), ...)`,
`delivery_enabled` has no `map.get` path at all, so nothing the caller passes in `--data` can flip
it. The runner's own flags file (`v3_fresh_units1_5_delivery_disabled.flags.yaml`) passes
`--data: '{}'` anyway — empty. The entire delivery/promotion branch (`switch: - condition:
${delivery_enabled}`, gating `require_delivery_contract`/`persist_delivery`) is therefore
unreachable this run regardless of what `--data` contained. On "cannot queue silently": the runner
checks `$execution.state -ne 'SUCCEEDED'` and throws otherwise — whether `gcloud workflows run`
blocks synchronously or the state check simply fails a still-QUEUED/ACTIVE execution, the design is
fail-closed either way; it does not treat a non-terminal state as success.

**3. Is the Unit 2 pilot configuration/bootstrap gate fail-closed and protected against expiry
during the run?** Yes. The BigQuery preflight (`20260827_preflight_fresh_v3_units1_5_pilot_v1.sql`)
requires: exactly one active config with **at least two hours of remaining validity**
(`effective_end > TIMESTAMP_ADD(v_checked_at, INTERVAL 2 HOUR)`) — not just "currently active,"
closing the expiry-during-run risk; that active config's every field matches the exact
Boat-approved pilot values I reviewed earlier this session (`RQ-20260827-2116`: 25/5%, 10/5%,
500,000/5%, `approval_reference='Boat-chat-20260827-UNIT2-PILOT-20260827-V1'`, `approved_by='Boat'`
— this is the live confirmation that the bootstrap operator I passed was actually approved and
executed); and the exact self-baseline magnitude run row exists with `compared_cells=39,
breached_cells=0, status='PASS'` — the same 39-cell figure from the pilot-limit proposal I
cross-checked in that earlier review.

**4. Is the disclosed mutation boundary honest?** Yes. The checker's `forbidden` list independently
asserts the runner contains no `scheduler jobs pause/resume/run`, no `workflows deploy`, no
`gs://interface-file`, and no `promotion_service_url` — and I confirmed by reading the workflow
YAML that the only path capable of writing to `gs://interface-file/` (the `derive_delivery_names`/
`gate_delivery_names` block, line ~872) sits behind the same `delivery_enabled` switch that is
hardcoded false. The restricted `rcb-bronze-zone` archive write the boundary discloses is real and
separate from delivery — it's the Unit 5 archive path, gated by whether Unit 5 has ready rows, not
by delivery.

**5. Does a threshold breach remain a hold and stay unable to be relabelled PASS?** Yes, and this
is the specific class of defect I found and BLOCKed earlier today in DDL 100 (a broad `WHEN`
intercepting a narrower one) — checked for it here specifically. In
`20260827_report_fresh_v3_units1_5_pilot_v1.sql`'s `CASE`, `WHEN magnitude_run_rows = 1 AND
magnitude_status = 'HELD_MAGNITUDE_REVIEW' THEN 'HELD_MAGNITUDE_REVIEW'` is the **first** branch,
evaluated before the `PASS_DELIVERY_DISABLED` branch. A breach sets `magnitude_status` to
`HELD_MAGNITUDE_REVIEW` (per DDL 063's own `IF(v_breached_cells = 0, 'PASS',
'HELD_MAGNITUDE_REVIEW')`), which the first WHEN catches unconditionally — it cannot fall through
to the PASS branch because CASE evaluates WHENs in order and stops at the first match. The PASS
branch additionally requires `breached_cells = 0` itself as a redundant second gate, so even a
CASE-ordering mistake would still be caught.

**6. Is terminal execution identity and post-run evidence strong enough for a separately approved
one-time production execution?** Reasonably strong, with one gap noted below (Note 2). The runner
requires `$execution.state -eq 'SUCCEEDED'` AND `$execution.workflowRevisionId -eq
$expectedRevision` before trusting the result, extracts `runId` and validates it
`StartsWith('V3NIGHTLY-')`, and only then calls the report query keyed to that exact `run_id`. The
report itself re-derives `production_delivery_rows` from `export_archive` joined to
`v3_unit5_payload_identity` scoped to this exact `pipeline_run_id` — not a global count — so a
prior run's delivered rows cannot leak into this run's disposition.

## Notes (non-blocking)

1. **Source-identity carve-out is narrow but real.** The em-dash/`?` exception in
   `build_v3_common_execution_census.ps1` only fires on comment-only lines and only for that one
   specific codepoint pair — it cannot mask a mismatch in executable YAML — but it does mean the
   "character-for-character identity" claim has one documented, scoped exception rather than being
   unconditionally absolute. Worth keeping narrow if this pattern is reused elsewhere.
2. **`gcloud workflows run` synchronicity is assumed, not proven from source alone.** The runner's
   correctness after the `gcloud workflows run` call depends on the returned `$execution` object
   already reflecting a terminal state (`SUCCEEDED`) rather than `ACTIVE`/`QUEUED`. I cannot verify
   from static text whether this specific gcloud subcommand blocks until terminal or returns
   immediately. Either way the design fails closed (a non-`SUCCEEDED` state throws), so this is not
   a safety gap — but worth an operator confirming the command's actual behavior once, since a
   surprising async return would make every `-PreflightOnly:$false` invocation throw immediately
   rather than silently misreport success.
3. Consistent with `docs/reviews/2026-08-27-759a0c2-e8e7364-claude.md`, I could not independently
   re-run the Unit 2 magnitude comparison this session; this review's confirmation that the
   preflight's exact `compared_cells=39` figure matches what I reviewed earlier is a self-
   consistency check across two artifacts, not an independent live re-derivation.

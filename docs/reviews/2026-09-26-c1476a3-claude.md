## Findings

**N1 — NEW deployment blocker: the shared dashboard's grain change affects consumers outside the
three objects.**
The fix changes `sap_data_engineer.sap_dashboard_carepay_installment` from one row per voluntary
OrderItem/Period to one row per OrderItem/Period/charge. The findings doc says deployment "would
replace exactly" three objects. Regression evidence covers only the RCL final wrapper
(and a dashboard full-row EXCEPT, which cannot detect ADDED rows). The repo shows at least these
direct readers: DDL 017, 021, 035, 048, 058, 079, 087, and operator
`20260827_monthend_missing_sap_installment.sql` / `20260826_v3_create_readiness_report.sql`.
Concrete impact, traced statically:

- **DDL 058 (V3 Unit 5).** `_candidate` combines the target rows with every other `_source`
  (dashboard) row for the same item (058 lines 273-318). Commit `63d6943` / integration `0c25117`
  adds `row_n != total_n` to `_spine_invalid_item` and changes the duplicate rule to per-period
  `DUPLICATE_PERIOD_IDENTITY`. With the new dashboard, a target item that has an extra receipt in
  any non-target period gets two rows for that period. The whole item would then be quarantined
  (`SPINE_INCOMPLETE` / `DUPLICATE_PERIOD_IDENTITY`). This fails closed, with no leak, but it is a
  silent hold regression in V3. It is not measured.
- **DDL 087.** `period_source_rows` / `exact_source_rows` count dashboard rows per item/period.
  Period-1 extras change those counts and possibly the hold classification.
- **DDL 091 (RCL_CMI)** is likely unaffected because compulsory keeps rank=1. Confirm this rather
  than assume it.

Required before deployment: list the live dependents of the dashboard
(`INFORMATION_SCHEMA.VIEWS` / routine definitions that mention it, not repo grep only), and give
each an added-row impact count. Consider the lower-risk design: leave the shared dashboard
byte-identical and source the additional receipts in a dedicated CTE or view used only by
RCL 05_newpayment. That removes the V3 blast radius. It also removes the two tie-driven dashboard
payload changes, which only appeared because the dashboard definition changed.

**N2 — honest labelling: 589 added payload rows, but only 80 are disclosed.**
`eir_regression.json` reports `added_payload_rows: 589` next to `added_additional_rows: 80`.
The findings table reports only the 80 additional rows. The other ~509 are most likely ordinary
Pending or unpaid spine rows for items that `additional_items` reopened. The reopen bypasses both
the 2-month recency window and the paid-period check at item level, so the wrapper re-emits the
full spine. That may be intended, because SAP validates the whole spine, but it needs three things:
(a) stating in the findings, (b) a breakdown by status or rank, and (c) confirmation that
re-sending already-interfaced Pending rows for those 75 items is idempotent on the SAP side.

**N3 — checklist item 4: no deterministic tiebreak.**
`ROW_NUMBER() ... ORDER BY create_time` still has no tiebreak. The author declined to invent a
business priority, which is right. But a technical tiebreak such as `ORDER BY create_time, id`
makes runs repeatable without choosing a business winner. Today the ordinary ExpectedReceived can
move between the two tied receipts on different runs (for example L77084511-V1 period 3 and
L77829701-V1 period 6). The `timestamp_rows = 1` guard correctly stops a flipped receipt from
replaying as an additional one. That guard is good, but it does not fix the instability of the
ordinary row.

**N4 — additional classification is inferred, not carried.**
Newpayment decides `is_additional_payment` from `ExpectedReceived = 0 AND ActualReceived > 0 AND
paid`. It does not use the dashboard's rank marker, which is dropped before the public 56 columns.
Any rank-1 row with ExpectedReceived=0 (for example a period-1 payment_amount equal to add_ons)
would take the additional path and skip the ordinary paid-period exclusion. The identity guard
reduces this risk, and the zero changed-row result suggests it did not happen in this snapshot.
Still, add one assertion that every added additional row comes from a charge with rank > 1.

**N5 — minor builder fragility.**
`build_rcl_additional_fix_20260926.py` asserts counts for the rank filter and CTE markers. It does
not assert counts for the `'    CTE_source,'`, `'finish AS (\n  SELECT'`, or two `WHEN` replacements.
Today each matched exactly once (confirmed by diff). A future drift in the baseline would change
them silently. Add `count == 1` asserts.

**N6 — pre-existing provenance issue, not introduced here.**
The captured LIVE definition of `sap_view.RCL_Motor_process_2_newpayment` begins with "Full
source-only legacy root-fix proposal ... this file does not replace or deploy the legacy view".
The object is live, so that comment is false. Whoever owns legacy provenance should reconcile it,
because a future reader may treat the live wrapper as undeployed.

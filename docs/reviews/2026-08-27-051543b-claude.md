## What was verified and holds up

- **56-column contract.** `sp_export_v3_scenario3_archive`'s `EXPORT DATA` column list (lines
  216-224) matches `v3_unit5_newpayment_delivery_ready`'s known 56-column order exactly (compared
  name-for-name against the same list used in `sql/operator/20260826_export_v3_onetime_create_manual.sql`),
  and the procedure independently asserts `v3_rcl_later_newpayment_ready` has the identical ordinal
  position/name/type to that canonical table via bidirectional `INFORMATION_SCHEMA.COLUMNS EXCEPT
  DISTINCT` (lines 131-151) — real cross-checking, not an assumed match.
- **Immutable-snapshot bijection (lines 152-159).** The `FULL OUTER JOIN` between the immutable
  `_snapshot` and the live mutable `_payload` (`v3_rcl_later_newpayment_ready`) correctly fails
  closed if the live view has drifted from what was snapshotted — including a schema reorder,
  since `TO_JSON_STRING` is ordinal-sensitive and the hash is recomputed fresh, not trusted from
  storage.
- **Transaction boundary around `EXPORT DATA`.** BigQuery cannot run `EXPORT DATA` inside a
  multi-statement transaction; the procedure correctly commits the claim+archive-ledger insert
  first, runs `EXPORT DATA` unguarded, then opens a second transaction to finalize state. A crash
  between the two leaves the claim in `PREPARING_ARCHIVE` — matching the claim's own description
  of "a recoverable hold," and the exclusivity `ASSERT` (lines 167-172) correctly still blocks a
  second attempt on the same flow/run until a human resolves or abandons it. `overwrite=false` on
  `EXPORT DATA` plus a fresh `export_run_id`-scoped URI on any retry prevents an accidental
  overwrite collision.
- **Parameter parity.** `sp_mark_v3_flow_exact_delivery`'s 12 params match the sentinel operator
  file's `CALL` order exactly, and its filename/generation/hash assertions correctly derive from
  the stored `v3_flow_export_claim` row rather than trusting caller input blindly.

## Hard finding — `vw_v3_flow_export_lifecycle`'s CASE makes its own duplicate-import guard dead code

Lines 476-478:
```sql
WHEN terminal_import_rows != 1 THEN 'PICKED_UP_PENDING_TERMINAL_IMPORT'
WHEN ARRAY_LENGTH(IFNULL(terminal_log_ids, ARRAY<STRING>[])) != 1
  THEN 'BLOCKED_IMPORT_LOG_ID_CARDINALITY'
```
`terminal_import_rows` is a raw `COUNTIF` of terminal rows per `file_name` (import_header CTE,
lines 396 and 393-396); `terminal_log_ids` is built with `ARRAY_AGG(DISTINCT ...)` over the exact
same terminal condition. By the time execution reaches line 476, `duplicate_log_id_rows > 0` has
already been ruled out at line 475, so within that file_name's group every terminal row has a
distinct `log_id` — meaning `terminal_import_rows` and `ARRAY_LENGTH(terminal_log_ids)` are always
equal at this point in the CASE. Line 476 fires on *any* value other than exactly 1, including
`> 1`, and labels it `'PICKED_UP_PENDING_TERMINAL_IMPORT'` — the same label used for the genuinely
healthy "not yet imported" case (`terminal_import_rows = 0`). Line 477's cardinality check can
therefore never be true when reached; it is unreachable dead code.

**This is not cosmetic.** A file imported twice under two different `log_id`s (the same "multiple
LogIDs" scenario this project's own
`docs/V3_SCENARIO1_MANUAL_FALLBACK.md` step 6 explicitly names as `AMBIGUOUS_ACK` and requires
distinct handling for) gets silently reported as ordinary pending progress instead of a blocked,
ambiguous state an operator needs to see. The `vw_v3_flow_export_lifecycle` view is the read
surface `sql/operator/20260827_report_v3_flow_lifecycle.sql` and DDL 101's Scenario 1 adapter both
rely on for lifecycle state, so this masks a real anomaly class across every flow that uses it, not
just Scenario 3.

**Required correction:** split the `terminal_import_rows` check so `= 0` and `> 1` are
distinguished (e.g. `WHEN terminal_import_rows = 0 THEN 'PICKED_UP_PENDING_TERMINAL_IMPORT'` ahead
of the existing cardinality check, or fold the `> 1` case directly into
`BLOCKED_IMPORT_LOG_ID_CARDINALITY` before the `= 0` pending case), then resubmit for a delta
review of just this view.

## Verdict rationale

One hard, well-reasoned finding: the lifecycle view's own intended safety net for duplicate/
ambiguous SAP imports cannot fire due to CASE-branch ordering, silently downgrading a documented
anomaly class to "normal pending" for every flow (Scenario 1 and Scenario 3 alike) that reports
through this view. Everything else in this large artifact — the transaction boundary around
`EXPORT DATA`, the immutable-snapshot bijection, the 56-column contract cross-check, and parameter
parity — held up under inspection. Fix the one CASE ordering issue and resubmit; no other change
requested.

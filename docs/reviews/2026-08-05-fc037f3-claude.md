## DDL 070 / 062 — the core fix

- **DDL 070**: adds `production_file_name STRING NOT NULL` to the `CREATE TABLE` path (fresh
  deploy) and a separate `ALTER TABLE ... ADD COLUMN IF NOT EXISTS production_file_name STRING`
  (nullable) for the already-live table. Checked live: `sap_delivery_manifest_v3` currently has
  **0 rows**, so the nullable-vs-NOT-NULL discrepancy between the two migration paths has no
  practical effect right now — worth a note for the record (the live table can never enforce
  NOT NULL retroactively without a rewrite), not a blocker.
- **DDL 062**: the closed-policy fix is `ASSERT p_sap_result_file_name=CONCAT('RCB_MOTOR_',
  p_production_file_name)` — the procedure itself derives and enforces the naming rule rather than
  trusting the caller to supply a correct pair. Both names are separately regex-validated
  (`^INSURANCE_RCB_...\.csv$` / `^RCB_MOTOR_INSURANCE_RCB_...\.csv$`), the replay guard now checks
  both names, and the INSERT stores `production_file_name` in the new column while `sap_file_name`
  now correctly holds the *SAP-reported* value — meaning the Apps Script ingestor's existing
  `sap_file_name = @file_name` match (unchanged) now compares against the right thing.
  Independently re-ran both dry-runs: 0 bytes each.

## Workflow — derivation timing and argument order

Traced the full diff: `sap_file_name` is removed from the workflow's own input args entirely (a
static scheduler no longer needs to supply it — directly resolving RQ-2129's claim 4).
`derive_delivery_names` computes both names from `source_parts[last]` — the *discovered* archive
object's own basename — strictly *after* `find_archive` has identified exactly one object, matching
"derives them only after exactly-one immutable archive-object census." `gate_delivery_names`
re-validates both names with the same two regexes as DDL 062, failing closed *before* attempting
the GCS copy if either is malformed. The promoter is sent only `production_file_name` (it has no
business knowing the SAP-result name). `gate_promotion` re-verifies the promoter's response against
the *requested* `production_file_name`, not a bare success flag. The final
`delivery_call_tail` passes `production_file_name` then `sap_result_file_name` — I checked this
against DDL 062's parameter order (`..., p_production_file_name, p_sap_result_file_name, ...`) and
they match positionally.

## Required review questions, answered directly

**1. Does the new logic enforce Boat's whole-item quarantine rule without weakening the 56-column
required-value contract or silently replacing required business data?** Yes. Nothing in the diff
touches `FORMAT('%.2f', ...)`, `CAST(... AS STRING)`, or any value-producing expression — the fix
adds a classification/exclusion layer *after* candidate assembly, not a change to how values are
derived. The final released-row assertion (`REGEXP_CONTAINS(TO_JSON_STRING(c),r':null|:"NULL"')`)
is unchanged from before; it still fires if a NULL somehow reaches `_candidate_release`, so the
contract is if anything strengthened (checked twice: once implicitly by construction, once
explicitly by the unchanged assertion).

**2. Are held and released item sets conserved, and can a held item leak into
`v3_unit5_payload_identity`, the producer hash, delivery-ready, or archive path?** Conserved and
no leak, traced directly:
- Conservation: `ASSERT (SELECT COUNT(DISTINCT OrderItem) FROM _candidate) = (COUNT(DISTINCT
  OrderItem) FROM _candidate_release) + (COUNT(*) FROM _candidate_required_hold)` — exact.
- Producer hash/count (`v3_unit5_newpayment_run_state`): computed `FROM _candidate_release c` only
  (line ~378) — held items never enter the hash.
- `v3_unit5_newpayment_ready` (the table everything downstream reads): populated `SELECT * FROM
  _candidate_release` only.
- `v3_unit5_payload_identity`: the INSERT explicitly filters `WHERE EXISTS (SELECT 1 FROM
  _candidate_release q WHERE q.OrderItem=c.OrderItem)` — a held item's identity rows are never
  written, and the row-count ASSERT conserves against exactly that same filtered set.
- Delivery-ready/archive tables are downstream of `newpayment_ready` and were not modified in this
  commit; since `newpayment_ready` itself is confirmed clean, this is a sound (not merely assumed)
  extension, though I did not re-read the downstream DDL this session to confirm it doesn't have
  its own independent read path around `newpayment_ready`.

**3. Are the hold ledger and release publication atomic/replay-safe under the existing run-state
claim, including zero-held and zero-released runs?** Yes. Both the new hold-table
DELETE-then-INSERT and the existing `newpayment_ready` DELETE-then-INSERT sit inside the same
`BEGIN TRANSACTION ... COMMIT TRANSACTION` block, after the unchanged `v3_unit5_newpayment_run_state`
claim MERGE (`WHEN NOT MATCHED THEN INSERT ROW` + `ASSERT @@row_count=1`, which still refuses a
second build for the same `pipeline_run_id`). Zero-held: hold DELETE+INSERT of 0 rows still passes
its `@@row_count=(SELECT COUNT(*) FROM _candidate_required_hold)` check trivially (0=0). Zero-
released: `STRING_AGG(...)` over an empty `_candidate_release` returns NULL, explicitly
`COALESCE`'d to `'<EMPTY>'` before hashing — confirmed this was already present, not newly broken
by the fix.

**4. Does excluding an entire item preserve complete `1..TotalPeriods` spines for every released
item?** Yes, and confirmed the ordering makes this structurally guaranteed, not just tested: the
full-spine completeness ASSERT (`NEWPAYMENT full period spine is incomplete`) runs over `_candidate`
*before* the hold/release split exists, so every OrderItem group in `_candidate` — including ones
later held — already has a complete, non-broken spine at that point. Because `_candidate_release`
is a **whole-OrderItem** filter of `_candidate` (never a partial-row filter), a released item's
spine is exactly its original complete spine, untouched. DDL 059's identity/balance conservation
was read as context only (not re-derived this session); given it consumes `newpayment_ready` the
same way it always did, and `newpayment_ready` now contains a strict subset of previously-eligible
OrderItems (never a mid-spine subset), nothing about DDL 059's own conservation logic should be
newly violated — but this is inference from structure, not an independent re-check of DDL 059 that
I performed line-by-line.

**5. Is using field names (not values) in `invalid_fields` PII-safe and sufficient audit evidence?**
Yes. The regex `r'"([^"]+)":(?:null|"NULL")'` against `TO_JSON_STRING(c)` requires the *value*
token to literally be the JSON `null` or the string `"NULL"` for a match — the captured group is
only ever the JSON key name preceding that exact null-shaped value, never a real data value. No
path exists in this regex for a real name/address/policy value to be captured. Sufficient as audit
evidence: it names exactly which of the 56 columns triggered the hold, without exposing the row's
actual (non-null) content in the ledger.

**6. Does the fix need an explicit notification/morning-report integration before deployment?**
Not a blocker for this delivery-disabled pilot. The durable, partitioned, queryable hold table
(`v3_unit5_candidate_required_hold`) is itself the audit trail Boat's rule requires; nothing in
this pilot's approved boundary promises automatic human notification. Worth flagging as a genuine
follow-up once this moves toward a delivery-enabled or recurring context, since a silently-growing
hold table with no alerting could let held items accumulate unnoticed — but that's a scope decision
for Boat, not a defect in this artifact.

**7. Any other candidate-wide assertion in DDL 058 that should remain fail-closed versus become
item-level?** Found one worth naming explicitly, per the request's own instruction not to expand
into an unrelated refactor: `POLICYNO_TOO_LONG` (`LENGTH(PolicyNo)>50`) and the Paid-completeness
check (missing InvoiceNo/PaymentDate/PaymentMethod/PaymentChannel on a Paid row) both still run
over `_candidate` — i.e., **before** the hold/release split exists — and both still abort the
*entire procedure* if violated anywhere in the full target set, not just quarantine the offending
item. This is a real asymmetry: the SQL-NULL case now gets graceful whole-item quarantine, but a
too-long PolicyNo or an incomplete Paid row on an otherwise-unrelated item still takes down the
whole run. I'm not suggesting this needs fixing here — Boat's stated rule was specifically about
the NULL incident, and broadening scope wasn't requested — but it's the direct answer to this
question and worth a conscious decision on whether the same item-level quarantine pattern should
eventually extend to these two as well.

**8. Rollback confirmation.** Confirmed exact — the diff to `sql/ddl/058_...sql` is additive/
structural only (new hold table, new temp tables, new assertions inserted between existing steps);
nothing about the existing table definitions or unrelated procedure logic changed in a way that
would make a `CREATE OR REPLACE PROCEDURE` redeploy of the prior source (`1f5c20c`/`6354d5b`)
anything other than a clean reversion. The new `v3_unit5_candidate_required_hold` table is additive
and independently inert if left unused by a reverted procedure — correctly, the request states it
must not be dropped or cleaned automatically on rollback.

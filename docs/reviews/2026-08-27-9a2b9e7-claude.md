## Standards / safety

1. **Assertion executes before `_validation_hold` can fan out `_hold` — confirmed by position.**
   The new `ASSERT` sits between the two `CREATE TEMP TABLE` statements in the file's textual and
   execution order; BigQuery scripting runs statements sequentially, so this ASSERT necessarily
   fires before `_hold`'s `LEFT JOIN _validation_hold vh USING(order_item,period,invoice_no)` can
   read a non-unique `_validation_hold`.
2. **SQL NULL grouping does not create a silent bypass.** `GROUP BY order_item,period,invoice_no`
   uses BigQuery's standard GROUP BY semantics, which treat NULL as equal to NULL for grouping
   purposes (distinct from `=` comparison semantics) — so two rows that both have a NULL
   `invoice_no` for the same `(order_item,period)` land in the same group and are caught by
   `HAVING row_count!=1`, not silently split into separate untested singleton groups. No bypass.
3. **Delta changes no readiness, payload, hold classification, or 56-column behavior.** Confirmed
   by the diff itself — no line inside `_candidate`, `_validated`, `_ready`, `_ready_identity`, or
   `_hold`'s CASE logic changed; only a new ASSERT was inserted between two existing statements.
4. **Checker would fail if the assertion were removed.** The new `require("Validation holds must
   be unique by order item, period, and invoice number" in ddl, ...)` line does a literal string
   search against the DDL text; removing the ASSERT (or its exact wording) removes the matching
   string and the checker's `require()` raises `SystemExit`. Ran it locally — genuine
   `V3_MONTHEND_ONETIME_STATIC=PASS` with the assertion present, confirming the checker text
   match is live, not decorative.

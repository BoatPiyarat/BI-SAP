## Checked against the request's own checklist

- **Empty-topic gate — behavior unchanged when blank**: `requestPostImportRefresh_`'s first line is
  `if (!config.postImportRefreshTopic) return;`, before the DDL 071 `CALL` and before the Pub/Sub
  fetch. With `POST_IMPORT_REFRESH_TOPIC` unset, neither the enqueue nor the publish ever runs —
  confirmed by reading the function top to bottom, not just the gate itself.
- **Outbox-before-publish ordering**: the `CALL sp_enqueue_v3_post_import_refresh(...)` (via the
  existing `query_` helper) executes and returns before the `event` object is built or
  `UrlFetchApp.fetch` to Pub/Sub is called. `query_` throws on a non-200 HTTP response or an
  incomplete job (`BQ_QUERY_<code>` / `BQ_JOB_NOT_COMPLETE`) — unchanged, pre-existing helper already
  relied on elsewhere in this file (e.g. `mergeHeader_`). If DDL 071's own `ASSERT`s reject the
  request (wrong manifest state, cross-manifest reuse, etc.), `query_` throws and the function
  returns before ever reaching the Pub/Sub call — no event can be published for a request the
  durable outbox itself refused.
- **Topic validation**: `POST_IMPORT_REFRESH_TOPIC` is validated in `getConfig_` against
  `/^[A-Za-z][A-Za-z0-9._~+%-]*$/` — matches GCP's own Pub/Sub topic ID character/start-with-letter
  rules — and only when non-empty (an unset property is still allowed to be blank/absent). An
  invalid value throws at config-load time, before `pollSapResultMailbox`'s main loop even starts.
- **Scope addition — narrow, no regression**: `sap_result_ingestion.appsscript.json` diff adds only
  `https://www.googleapis.com/auth/pubsub`; the previously-reviewed scope set
  (`gmail.modify`/`bigquery`/`devstorage.read_write`/`script.external_request`/`script.send_mail`/
  `script.scriptapp`) is otherwise untouched — `cloud-platform` is not reintroduced. `pubsub` is the
  only OAuth scope Google exposes for this API (there is no narrower publish-only scope at the
  Apps Script manifest level), so this is the minimum available grant, not an over-broad choice.
- **Retry behavior**: on a Pub/Sub publish failure (non-200), the function throws
  `POST_IMPORT_PUBSUB_<code>` — this happens *after* the enqueue already committed, so the outbox
  row durably exists as `PENDING` (idempotent per DDL 071's review). Because the throw happens
  before `group[0].message.getThread().addLabel(...)`, the email is never marked `ingested` and will
  be re-picked-up by the next poll — `persistCandidate_` and `requestPostImportRefresh_` both re-run
  safely (the enqueue call is a no-op the second time; a duplicate Pub/Sub publish is an acceptable
  at-least-once event for a downstream dispatcher expected to key off the same idempotent LogID).
- **No trigger/deployment action requested**: this commit only edits source `.gs`/`.json`/`.md`
  files. No trigger install, Gmail action, GCS write, or BigQuery mutation occurs by reviewing it.
- **Evidence re-verified independently, not trusted from the commit message**: copied the `.gs` to
  `.js` and ran `node --check` — passes. Ran `git diff --check c90d79b^ c90d79b` — passes, no
  trailing whitespace or conflict markers.

## Observation (not a required note)

`requestPostImportRefresh_` is called inside `pollSapResultMailbox`'s `Object.keys(byRun).forEach`
with no per-run try/catch, same as the pre-existing `persistCandidate_` call right above it — a
throw from any one run aborts the whole poll cycle, including runs unrelated to the failure. This
pattern already existed before this commit (already implicitly accepted via `persistCandidate_`'s
own BigQuery-failure exposure, reviewed in `docs/reviews/2026-08-04-1e949e7-claude.md`); this delta
adds one more thing that can throw in that same all-or-nothing loop — an external Pub/Sub HTTP call,
which has a different failure profile (transient network/quota issues) than the existing BigQuery
calls. Not a regression introduced by poor design here, and the 15-minute poll cadence still bounds
how long a stranded item waits, same reasoning already accepted for this poller. Worth a look if
`POST_IMPORT_REFRESH_TOPIC` is deployed and this proves to matter in practice, but not blocking.

## What this unit does

Adds a durable "activate a scenario's Cloud Scheduler job" control plane: register immutable
scheduler-inventory evidence (`sp_register_v3_scheduler_inventory_evidence`), record a human
approval tied to an exact readiness row (`sp_register_v3_scenario_activation_approval`), capture a
scheduler prestate and claim the activation (`sp_claim_v3_scenario_activation`), finalize only after
independently reproving zero schedule overlap against the flow's own cron definition
(`sp_finalize_v3_scenario_activation`), and roll back to an exact byte-verified prestate
(`sp_record_v3_scenario_rollback`). `scripts/build_v3_scheduler_inventory.py` is the evidence
generator the SQL trusts by contract (generator string, source API, pagination-complete flag).

## Checklist 1–12

2. **Provenance — PASS.** Builds on the already-reviewed `vw_v3_business_flow_activation_readiness`
   (DDL 096) and `sp_mark_v3_exact_delivery` pattern without re-deriving anything.
3. **NULL-safety — PASS, and notably fail-closed by design.** Every gate is a single large
   `ASSERT ... AND ... AND ...` chain; in BigQuery, `ASSERT` raises on both `FALSE` and `NULL`, so
   any `SAFE_CAST` or `JSON_VALUE` miss inside these chains fails the whole assertion rather than
   silently passing — the correct default for this class of gate. One genuine but low-risk edge:
   `fn_v3_cron_field_matches` computes `MOD(candidate_value-range_start, step_value)` with
   `step_value` defaulted via `IFNULL(...,'1')`; a malformed cron atom like `*/0` in the submitted
   evidence would make `step_value=0` and `MOD(x,0)` is a runtime error in BigQuery, not a
   graceful `ASSERT` failure. Given the input is Cloud Scheduler's own API response (not
   attacker-controlled), this is acceptable, but it fails loud/ungraceful rather than with the
   project's usual named `ASSERT` message — worth a one-line comment or an explicit
   `SAFE_DIVIDE`/guard if this is touched again.
4. **Ordering — PASS.** `GENERATE_TIMESTAMP_ARRAY(horizonStart, horizonEnd - 1 minute, 1 minute)`
   in the SQL's independent cron re-expansion matches the Python generator's
   `while cursor < end: ... cursor += 1 minute` loop exactly (same inclusive/exclusive bounds) —
   verified by reading both side by side, not run.
5. **Column order — N/A.** No interface file column changes.
6. **Grain — PASS.** `flow_key` + `evidence_run_id` + `approval_id`/`activation_id` grain is

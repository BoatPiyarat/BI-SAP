## What changed

`_exports` now requires `AND i.payload_hash = a.payload_hash` in addition to the existing
`USING (order_item, period, charge_id)` natural-key join.

## Verification

Exactly closes the gap named in the prior review: a stale `export_archive` row sharing the same
`(order_item, period, charge_id)` from an earlier pipeline run can no longer satisfy the current
run's `_exports` unless its `payload_hash` also matches, which only happens for a genuine re-export
of identical content. Both sides of the new predicate are the same `payload_hash` column already
present on `v3_unit5_payload_identity` (`STRING NOT NULL`) and `export_archive` (`STRING`) —
confirmed by re-reading both `CREATE TABLE` statements — so no schema change was needed, this is a
one-line tightening exactly as recommended.

## Minor observation (non-blocking)

`export_archive.payload_hash` has no `NOT NULL` constraint. If any historical `export_archive` row
were ever written without a `payload_hash` (none currently are, based on every writer reviewed today
— `048`, `060`, `069` — always populating it), the new `AND` would make that row silently unmatchable
rather than falling back to the natural-key-only behavior. Given every current writer populates the
column, this is theoretical today, not a live risk — noting only so it isn't rediscovered as
"exports mysteriously stopped counting" if an older or third write path ever omits it.

## 1. ⚠️ CANCEL PATH 2025 — investigated, real gap confirmed, but smaller and more specific than
   the raw NO_NEW_PAID_2025 number suggested. **Needs Boat's call before Phase C, not a fix I made.**

### The question: for 2025 orders that are cancelled in CareOS and already exist in SAP, does the
pipeline generate anything a future cancel-export step could use as a baseline?

**Short answer: currently 0, and the fix isn't "make expected_state carry a Cancelled status" —
it's more layered than that. Full breakdown:**

Total 2025 order_items (`stg_order_dim`, `is_cancelled = TRUE`, year via
`GREATEST(OrderDate,PolicyDate)` basis): **18,249**

| Split | order_items | Meaning |
|---|---:|---|
| Not yet in SAP at all | 109 | Correctly excluded already, logged as `CANCEL_2025_NOT_IN_SAP` (45, have a schedule row so they made it into `sap_excluded_records`) or invisible for the same reason as the row below (64, no schedule row — see next section) |
| **Already in SAP, fully Cancelled there already** | **10,153** (8,187 + 1,966) | SAP already reflects the cancellation. No action needed for these — not a gap. |
| **Already in SAP, SAP has NOT caught up yet (some period still Pending/Paid in the mirror)** | **9,953** | **These are the real "should get a cancel document" population. Pipeline generates a cancel row for 0 of them today.** |

Breaking the 9,953 down further — this is the part that changes the picture:

| Sub-group | order_items | periods | Why it's invisible / mislabeled |
|---|---:|---:|---|
| Genuine standalone cancellation, **has a `stg_schedule` row** (flows through the engine) | **328** | 790 | Enters `expected_state` today, but `expected_state.expected_status` only ever computes `Paid`/`Pending` — there is no `Cancelled` value in the schema at all. These 328 are silently mislabeled, not silently dropped. |
| **Credit-Shell change-order supersession** (`old_human_id` in `careos.cancelled_change_orders`), **no `stg_schedule` row** | **9,625** | 21,770 | `stg_schedule`'s own source query deliberately excludes `old_human_id` rows (`WHERE o.human_id NOT IN (SELECT old_human_id FROM cancelled_change_orders)`) so the superseding new order isn't double-scheduled. Verified via 3 samples (L77238827, L79216708, L78513502): all 3 are confirmed superseded orders with a real linked transaction — this is the *existing*, deliberate change-order exclusion working as designed, not a new bug. |

**Verified, not assumed**: sampled 3 order_items from the 9,625 group directly against
`careos.careos_orders`/`carepay_transactions`/`cancelled_change_orders` — confirmed all 3 have
`matching_txn_count = 1` (a transaction genuinely exists) and `is_superseded_old_order = 1`. Then
re-ran the full split with `COUNT(DISTINCT order_item)` (first pass double-counted via a
fan-out join against `cancelled_change_orders` — caught before reporting, since that table can have
>1 row per `old_human_id`).

### What this means, plainly:
- The 328 genuine-cancel group is a real, clean, small gap: expected_state has no way to represent
  "this should be Cancelled." That's a schema/design gap in `expected_state`, confirmed with 0
  currently generated — matches Boat's own "if 0, fix the design" criterion.
- The 9,625 change-order group is **not a new problem** — it's the same open question already
  parked with Aware (Q3a, `docs_considered > 1`, `SAP_CANCEL_IMPORT_SPEC_INFERRED_v0.9.md`,
  per `INPUTS_NEEDED.md`). Whether a superseded old order needs its own explicit SAP cancel
  document, or whether the replacement order's own document supersedes it in SAP's own picking
  logic, is exactly what that open question is about. I did not attempt to resolve it — flagging
  the overlap so whoever builds Phase C's cancel branch knows these ~9,625 items are the SAME
  unresolved question, not a separate one.
- **Downstream impact, quantified**: of `interface_daily_status`'s current 9,372 distinct
  `STATUS_CONFLICT` items, **6,497 (69%) are this exact 2025-cancel-mislabeling population**
  (23,222 of 34,758 STATUS_CONFLICT rows). This is likely most of what's left in STATUS_CONFLICT
  today. Not fixed this session (no design call to make it on my own) but now quantified instead of
  unexplained.

**Nothing here was written to `sap_excluded_records` or `expected_state` differently than what's
already live — this section is pure investigation, no new deploy.**

## 3. F2 — PolicyNo > 50 chars = BLOCK

**Written, NOT deployed**: `sql/ddl/035_policyno_too_long_validation.sql` — full
`sp_run_validation()` procedure (BigQuery routines have no ALTER-to-add-a-check; every versioned
file carries the complete body, same convention as 017/034), existing 4 checks unchanged, new
`POLICYNO_TOO_LONG` check appended. Source is `stg_order_dim.policy_no` (from 033, verbatim
`careos_order_items.policy_number`, no transform). Committed to git (Rule 4) but **the CREATE OR
REPLACE PROCEDURE has not been run against BigQuery** — `sp_run_validation` in production is still
the 4-check version from 017.

**Verified read-only against current `expected_state`** (so these numbers hold regardless of
whether/when 035 gets deployed): **28 rows / 11 distinct order_items** have `policy_no` over 50
chars. All 3 sampled examples are the same pattern — upstream `policy_number` holds an operational
status note in Thai (e.g. `"แจ้งงานแล้ว/ต่ออายุ/ไม่รวม พรบ./กรมธรรม์ 260901/M003006545"`, meaning
roughly "notified/renewal/excl. compulsory/policy 260901/M003006545") instead of, or in addition
to, a real short policy number — not a case of a policy number that's genuinely 51-58 characters.
Truncating would silently corrupt the field; blocking for manual review is the right call per
Boat's rule.

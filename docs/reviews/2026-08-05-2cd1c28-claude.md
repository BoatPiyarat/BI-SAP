`label:"notification SAP upload" -label:"ingested" from:... subject:"[LIVE]" newer_than:1h`

The ambiguity check (line 34) is now `if (group.length !== 1 || logIds.length !== 1)`, and the

## One non-blocking observation for the rehearsal, not a new required note

`-label:"ingested"` exclusion, like `.addLabel()`, operates at Gmail **thread** granularity. If a
genuinely different, not-yet-processed result message ever landed in the *same thread* as an
already-ingested one (plausible only if Gmail's threading groups two distinct LogID
notifications together, e.g. via a shared/reused subject), the whole thread — including the new
message — would now be excluded from every future search once the thread carries `ingested`,
and the heartbeat would not catch this: `checkSapResultIngestionHeartbeat` only tracks whether the
poll function itself keeps succeeding, not whether every individual result message got processed,
so a thread-level miss like this would be silent. I have no evidence this sender's emails actually
thread together this way — each notification's subject likely embeds the run-specific file name,
which would keep them in separate threads in practice — so I'm not blocking on it. Suggest adding
it as one more rehearsal case (two distinct LogIDs deliberately forced into one thread, if
feasible to construct) alongside the ones already listed in the deployment doc, given the
heartbeat mechanism can't detect this failure mode on its own.

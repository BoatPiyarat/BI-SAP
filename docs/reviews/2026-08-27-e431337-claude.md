## What I traced and confirmed correct

- **Mutex actually serializes, not just decorates.** `sp_claim_v3_common_scheduler_cutover`
  pre-checks for an existing `CLAIMED`/`ACTIVATED` row *before* the transaction, then re-checks the
  identical condition *again* inside the transaction immediately after `UPDATE
  v3_common_cutover_mutex SET lock_version=lock_version+1`. Under BigQuery's snapshot-isolated
  multi-statement transactions, two genuinely concurrent claims both updating the same mutex row
  cannot both commit — one aborts with a serialization conflict, rolling back its own INSERT too.
  The pre-transaction check alone would have a TOCTOU gap; the mutex closes it. This is the same
  correct pattern already used in DDL 098 (which I reviewed and passed earlier today).
- **Config-hash vs. state-transition separation is deliberate and correct, not a bug.** I initially
  read `legacy_config_hash`/`v3_config_hash` as suspicious — at finalize time the V3 job's `state`
  *must* change (PAUSED→ENABLED) while the hash is asserted unchanged. Tracing the hashed STRUCT
  (`resource_name, schedule, time_zone, attempt_deadline, retry_config, http_target`), `state` is
  deliberately excluded. The hash proves the job's *definition* wasn't tampered with during cutover
  (no schedule drift, no retargeted endpoint); the actual PAUSED/ENABLED transition is checked
  separately via explicit `JSON_VALUE(...,'$.state')` assertions. Two different properties, checked
  by two different mechanisms — correct.
- **Overlap check is sound given both jobs share one cron.** Both `sap-extract-schedule` and
  `v3-nightly-orchestrator` are hardcoded to the identical `30 20 * * *` / `Asia/Bangkok` — matching
  the live state confirmed in today's session notes (`sap-extract-schedule` ENABLED at 20:30 ICT;
  V3 Scheduler PAUSED at the same cron). Since a PAUSED job contributes zero `windows` in the
  evidence generator (`build_v3_scheduler_inventory.py` only computes windows for `state ==
  "ENABLED"`), the finalize/close overlap checks correctly reduce to "the job being disabled must
  actually show zero windows," which is exactly what enforces the pause-before-enable ordering.
- **Bootstrap-run exclusion cross-checks against DDL 099, which I reviewed independently earlier.**
  The magnitude-PASS gate requires `m.pipeline_run_id != m.baseline_run_id`, correctly excluding
  DDL 099's self-baseline bootstrap row (where `pipeline_run_id = baseline_run_id` by construction)
  from counting as the "fresh non-bootstrap PASS" this procedure requires.
- **View CASE has no swallowed-branch defect.** Checked specifically for the class of bug I found
  in DDL 100 (a broad `WHEN` condition intercepting a narrower one below it) — each `cutover_state`
  value here maps to a mutually exclusive branch; no case is unreachable.
- **Manual fallback is genuinely read-only and correctly scoped.** No `CREATE`/`ALTER`/`INSERT`/
  `UPDATE`/`MERGE`/`CALL`/`EXPORT` anywhere in it (also asserted by the checker script); it reports
  the durable restoration target and the correct `ABORTED` vs. `ROLLED_BACK` transition based on
  current state, but never performs the Scheduler mutation itself.
- **Static checker matches the source it checks.** Spot-verified several of its assertions
  (procedure list/order, transaction count, evidence-type literals, hardcoded cron/timezone
  literal counts) against the actual DDL text — all accurate, not aspirational.

## Notes (non-blocking)

1. **`p_workflow_revision` is trusted input, not independently verified against a live source.**
   Nothing in BigQuery can confirm the string an operator supplies actually matches the currently
   deployed Workflow revision — this is a known, accepted limitation shared with every other
   evidence-registration procedure in this project (Cloud Scheduler/Workflows state lives outside
   BigQuery), not a new gap introduced here.
2. **Single-reviewer risk.** Given the scale (622 lines, production Scheduler control, singleton
   mutex, six-way hash cross-checks) and that this is a one-pass static read with no live
   BigQuery/Workflows access, I'd treat this as a strong first PASS rather than a final sign-off —
   worth a second reviewer's eyes (Codex's own review workers, once available) before the first
   real CALL, per the artifact's own "NOT DEPLOYED" header.

   all-six-thresholds, all-three-approval-fields) sit between the declarations and the `CALL`,
   confirmed via direct text-order check (`text.index(...) < text.index("CALL")`), not just
   presence. Ran the checker locally — genuine `V3_UNIT2_BOOTSTRAP_OPERATOR_STATIC=PASS`, not
   aspirational.
2. **Thirteen-argument order matches DDL 099, no coercion or silent default.** Read DDL 099's
   procedure signature directly: `p_baseline_run_id, p_config_id, p_effective_start,
   p_effective_end, p_records_absolute, p_records_percentage, p_orders_absolute,
   p_orders_percentage, p_amount_satang_absolute, p_amount_percentage, p_approval_reference,
   p_approved_by, p_approved_at` — thirteen parameters, exact order, exact types. The operator's
   `CALL` passes `v_baseline_run_id` plus the same twelve human variables in identical order, and
   the checker independently regex-asserts this exact argument list. No coercion in the CALL
   itself (types declared on both sides match: STRING/TIMESTAMP/INT64/NUMERIC).
3. **Duplicate active config, config-ID replay, and baseline replay fail closed — confirmed at
   both layers.** The operator has three preflight ASSERTs (active config exists / config_id
   exists / baseline already has a magnitude result) *before* the CALL, and DDL 099's procedure
   body repeats all three checks again inside its own trusted boundary (plus a fourth: the
   baseline must already have exactly one successful `UNITS_2_5_ARCHIVE` row and a Unit 2
   summary, and must NOT already have distribution evidence). Defense in depth, not just a single
   client-side gate that a direct `CALL` could bypass.
4. **Postchecks bind exact approved values and conserve magnitude-result/distribution cells.**
   The operator's postcheck ASSERTs re-select the committed config row matching every one of the
   nine approved field values (using `IS NOT DISTINCT FROM` for the nullable `effective_end`,
   correctly NULL-safe), confirm the self-baseline run row has `breached_cells = 0` and
   `status = 'PASS'`, confirm distribution rows exist, and confirm the count of zero-breach
   magnitude-result rows equals the distribution row count — a real conservation check, not a bare
   row-count-parity claim, since it specifically requires `ARRAY_LENGTH(breach_reasons) = 0` on
   every result row (i.e., every cell computed clean, not just present).
5. **Cannot export, write GCS, mutate Scheduler, or call any other procedure — confirmed.** Only

## Spec / arithmetic axis

1. **DDL 063's breach predicate, recomputed from source.** Read the actual CASE/IF logic (lines
   204–220 of `063_v3_unit2_population_magnitude_gate.sql`):
   `IF(ABS(current - baseline) > absolute AND ABS(ratio) > percentage, [reason], [])`, independently
   for records, orders, and amount, then `ARRAY_CONCAT`'d into `breach_reasons`. This exactly
   matches the proposal's stated semantics ("absolute breach AND percentage breach" independently
   per field) — not a paraphrase I'm trusting, but the literal predicate structure.
2. **39 cells / 15 breached / 11 record / 15 order / 6 amount — not independently re-run this
   session (no BigQuery access), but internally consistent.** 15 breached cells with 11+15+6 = 32
   total reason-flags is arithmetically plausible (a single cell can breach on more than one of
   the three dimensions simultaneously, as the six shown rows demonstrate — e.g., the
   `PAYMENT_EVENT/ONETIME/Paid` row breaches all three). Not a red flag on its face.
3. **Force-pass absolute boundaries (1,065 records / 498 orders / 497,720,770 satang) — verified
   against the six rows shown in full.** `SCHEDULE/RCL/Pending` shows the largest record-count
   change (-1,065), `SCHEDULE/RCL/Paid` shows the largest order-count change (+498), and
   `PAYMENT_EVENT/ONETIME/Paid` shows the largest amount change (-497,720,770 satang) — all three
   force-pass figures match the largest-magnitude value in their respective column among the six
   fully-shown rows exactly. I cannot verify these remain the maxima across the other nine
   breached cells the proposal only summarizes (not shown in the table), since I have no live
   query access — flagged as a note, not a blocker, given the six shown rows already produce
   these exact figures and the other nine are described as smaller categorical/hold cells.
4. **Pilot limits honestly labelled as risk policy, not data-fitted approval advice.** Confirmed
   directly in the doc text: "These values are a conservative operational risk policy, not a fit
   to observed data and not a recommendation to make a particular run pass." This is the opposite
   of data-fitting — the proposal picks round, conservative numbers and then *reports* that they
   correctly refuse to pass the current comparison, rather than picking numbers that would pass it.
5. **Verdict and post-approval scope stated below.**

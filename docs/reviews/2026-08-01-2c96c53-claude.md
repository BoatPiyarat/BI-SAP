## Notes (non-blocking)

1. **Inert tiebreak in 024**: within `PARTITION BY DocEntry`, the final `DocEntry DESC` is a no-op
   (it is the partition key). Residual nondeterminism window: same DocEntry with two *different*
   post-DISTINCT rows sharing (UpdateDate, UpdateTime) — a sub-minute double update. No worse than
   the old BatchRunDate ordering (coarser), but worth one cheap follow-up count when 024 next runs.
2. **`MAX(open_period_start)`** in 037 takes the latest row across all periods. A future-period row
   inserted early would clamp everything prematurely. Fine while Boat inserts one row per close;
   consider a `WHERE` on the intended period or a sanity ASSERT (`open_period_start <= CURRENT_DATE()`).
3. **Date-basis conflict is still open** (flagged honestly by the author in
   `FINDINGS_INSURER_EXCLUSION_RISK_20260731.md`): 037's exclusion `date_basis` still uses
   `GREATEST(OrderDate, PolicyDate)` while the locked July scope basis is `PaymentDate` (R13).
   RULE-01's clamp lands correctly; the basis alignment is a separate decision Boat must schedule.
4. Stale comments in `018`/`030` still name `PROVISIONAL_PENDING_AWARE_Q3A` (comments only — no code
   filters on the literal; verified by grep).
5. `DATE(UpdateDate)` truncates a TIMESTAMP at UTC. The shift is constant, so *ordering* is
   unaffected (monotonic transform) and this is safe for the tiebreak; just don't compare the
   column against ICT calendar dates without noting the timezone.
6. Sequencing (author already states it): 025 strict validation and any 043 dry-run against the live
   mirror are only meaningful **after** reviewed 024 is applied/refreshed — deploy order 044 → Boat's
   period row → 024 → refresh → 025 → 037.

**Named risk (anti-rubber-stamp):** note 2 — a wrong/future `sap_period_lock` row silently clamps
every July PaymentDate; the table has no validation and 037 trusts `MAX()` blindly. Human-input
control table + ASSERT is the cheap mitigation.

## BLOCK 1 — CONFIRMED: ARRAY inequality is not valid BigQuery

`035`'s new `SCHEDULE_PERIOD_SET_INVALID` predicate ends with
`actual_periods != GENERATE_ARRAY(1, total_periods)`. Reproduced standalone (0-byte dry-run,
2026-08-01): **`Inequality is not defined for arguments of type ARRAY<INT64>`**. 035 is a
procedure, so a file-level dry-run is blind to this (the standing late-binding lesson); the
statement fails at CALL. The RQ's own request to review "array comparison syntax" was the right
instinct. Fix — either form works; the second avoids serialization entirely because
`actual_periods` is DISTINCT-sorted, so length+min+max fully determine the set `1..N`:
- `TO_JSON_STRING(actual_periods) != TO_JSON_STRING(GENERATE_ARRAY(1, total_periods))`, or
- `ARRAY_LENGTH(actual_periods) != total_periods OR actual_periods[OFFSET(0)] != 1 OR
   actual_periods[ORDINAL(ARRAY_LENGTH(actual_periods))] != total_periods`.
(`GENERATE_ARRAY(1, NULL)` returns NULL harmlessly; the `total_periods IS NULL` disjunct already
routes those rows.)

## BLOCK 2 — 013 qualification gate: population change without measurement or audit trail

The LEFT→INNER JOIN rewrite (order resolution + non-empty `human_id` + `LEAD_STATUS_PURCHASED`)
implements Boat's rule 2 semantics — not disputed. But it silently narrows a **money-bearing**
staging population, and:
1. **No before/after delta was measured.** The E1 tier change set the standard: population-changing
   predicates ship with a measured transition count. Required here: how many SUCCESSFUL charges /
   staging rows drop, split by failure reason (no order · empty human_id · lead not PURCHASED).
2. **The dropped orphans are invisible.** The canonical spec's own header says
   `EXCLUDED != DELETED … separately auditable` — yet these rows vanish at staging with no
   register/validation row and no logged count (they cannot enter `sap_excluded_records`, which is
   `(order_item, period)`-grain, precisely because they have no order_item). Minimum fix: log the
   per-reason drop counts into `pipeline_run_log`'s message on each 013 refresh, or write a
   charge-grain diag row class. Deploy of the new 013 is blocked until both items exist.

## Canonical document — sound, four precision notes (fix with the BLOCK round)

1. Rule 15 "preserve raw PaymentDate" — word it per RULE-08: CareOS remains the original;
   `payment_date_clamped` is the durable marker; **no stored duplicate** of the raw date.
2. "Winner selection uses UpdateDate, UpdateTime, DocEntry recency" — true only at
   `(OrderItem, Period)` grain (025 layer 3–4). Per-DocEntry mirror dedup (024/043) now uses the
   **content-hash** tiebreak; say so, or this file re-canonizes the pre-`1a8216f` rule.
3. Rule 13 records Boat's supersession but doesn't cite the original item number (16) the way
   rule 9 cites item 11 — add it for traceability.
4. `FORMAT('%d', NULL)` yields a NULL reason string for exactly the malformed rows the schedule
   check flags (verified: returns NULL, not an error) — wrap with `IFNULL(total_periods, -1)` or
   `%t` so the register row stays self-describing. Also, `MAX(total_periods)` per item masks
   intra-item disagreement; cheap to add `COUNT(DISTINCT total_periods) > 1` to the same check.

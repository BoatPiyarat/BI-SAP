# Review — RQ-20260805-1950-post-import-watchdog

Reviewer: Claude Code
Artifact: commits `f6d7151`, concurrency deltas `cdb5843`, `8fbbb93`, tests `fd56e28`;
`infra/post_import_watchdog/` and Workflows client dependency bump.
Verdict: **PASS**

## Checked against the request's own checklist

- **Required configured thresholds**: `configured_seconds` requires `CLAIM_TIMEOUT_SECONDS` (60–
  3600), `EXECUTION_TIMEOUT_SECONDS` (300–7200), `CANCEL_WAIT_SECONDS` (30–600) — all bounded,
  all fail closed (missing or out-of-range raises) rather than silently defaulting. README states
  "No timeout is silently selected in source," confirmed by reading `main()`: there is no fallback
  value anywhere for these three.
- **Candidate selection/age handling**: `WHERE request_status IN ('CLAIMED','STARTED') ORDER BY
  claimed_at LIMIT 100`; `age_seconds` is computed from `claimed_at`, which both `sp_claim_...` and
  `sp_bind_...` (DDL 072) set/preserve identically — a valid shared age reference for both states.
- **Release attempt boundary**: stale `CLAIMED` rows (`age_seconds >= claim_timeout`) call
  `sp_release_v3_post_import_claim`; the alert for exhausted attempts only fires when
  `released and attempt_count >= 3` — matching DDL 072's own "stop at three" bound (reviewed under
  RQ-1928).
- **Workflows state mapping and cancel-and-poll ordering — the core race-safety claim, traced in
  full**: for `STARTED` rows, if the execution is `ACTIVE`/`QUEUED` and still within
  `execution_timeout`, the watchdog takes no action at all — it never touches a genuinely healthy,
  in-flight execution. Once overdue, it calls `cancel_until_terminal`, which polls
  `get_execution` in a loop until the state leaves `ACTIVE`/`QUEUED` (or raises after
  `cancel_wait_seconds` if it never does) — so `TIMEOUT` can never be recorded while the execution
  is still actually running.
- **Terminal completion race behavior (`cdb5843`, `8fbbb93`) — independently re-verified by running
  the tests, not just reading them**: ran `python -m unittest test_main -v` after installing the
  package's own declared dependencies — all 4 tests pass, including
  `test_cancel_race_returns_already_succeeded` (cancel raises because the execution already
  finished on its own; `cancel_until_terminal` correctly re-fetches and returns the real state
  instead of propagating the exception) and `test_cancel_polls_until_cancelled` (normal poll-loop
  path). `cdb5843` additionally wraps `release_claim`/`complete` in try/except: if the underlying
  DDL 072 procedure's own `ASSERT @@row_count=1` fails because a concurrent process (the workflow
  itself, or another watchdog run) already moved the row past the expected state, the watchdog
  re-checks the row's *current* status and treats "someone else already handled this" as a benign
  no-op (returns `False`, doesn't increment `actions`, doesn't double-alert) rather than crashing
  the whole batch on one row's race.
- **The exact TIMEOUT-vs-HUMAN_ACTION split the request calls out**: `8fbbb93` fixes what was
  previously an unconditional `TIMEOUT` after any cancel attempt — now, if the state after
  cancellation turns out to be `SUCCEEDED` (the execution actually finished successfully right as
  the watchdog tried to kill it), the outcome is `HUMAN_ACTION` with template
  `WORKFLOW_TERMINAL_WITHOUT_OUTBOX_COMPLETION` — correctly refusing to mislabel a real success as
  a timeout. Any other post-cancellation terminal state (`FAILED`/`CANCELLED`) still records
  `TIMEOUT`. Separately, if the execution was *already* terminal (not `ACTIVE`/`QUEUED`) the moment
  the watchdog first checked it — meaning the workflow finished on its own without ever calling
  `sp_complete_v3_post_import_refresh` — that also becomes `HUMAN_ACTION` with the same template,
  regardless of whether the workflow itself succeeded or failed. This matches the claim precisely:
  "Other terminal-without-completion states become `HUMAN_ACTION`."
- **Alert payload/IAM**: `publish_alert`'s body is `component`, `log_id`, `attempt_count`,
  `workflow_state`, `error_template` only — no order, customer, or file-content data. README
  documents a dedicated service account scoped to BigQuery job/dataset access,
  `workflows.executions.get`, `workflows.executions.cancel`, and publish on the *one* existing
  `v3-orchestrator-alerts` topic — reusing the same alert channel as the rest of this pipeline
  rather than introducing a new one.
- **Bounded result set**: `LIMIT 100` on the candidate query — one watchdog run cannot process an
  unbounded backlog.
- **No job, scheduler, IAM, workflow cancellation, alert, procedure CALL, or BigQuery mutation
  occurred in this review**: I read the source and ran the *unit test suite* (which mocks the
  BigQuery/Workflows/Pub/Sub clients entirely — no real GCP call was made). I did not execute
  `main()` itself, which would require live credentials and configuration this review does not
  have or need.
- **Evidence re-verified independently**: `python -m py_compile infra/post_import_watchdog/main.py`
  passes; `git diff --check` passes clean on all three commits (`f6d7151`, `cdb5843`, `8fbbb93`).

## Minor observation (not blocking)

After a forced cancellation, only `SUCCEEDED` is special-cased into `HUMAN_ACTION`; a post-cancel
`UNAVAILABLE` state (a real, if rare, Workflows execution state distinct from
`FAILED`/`CANCELLED`) would fall through to `TIMEOUT` by the current `else` branch. This doesn't
lose the row — it still gets completed and alerted — it's just a slightly imprecise label for a
state that isn't quite "we successfully forced it to stop." Not required before deploy.

## Verdict

PASS. The watchdog correctly never marks an actually-running execution as timed out, correctly
distinguishes a genuine forced-timeout from a race where the execution secretly succeeded, and
tolerates benign concurrent-completion races against the dispatcher/workflow itself without
crashing its own batch. Independently ran the included unit test suite (4/4 pass) rather than
trusting the commit's own claim. No production action, IAM change, or BigQuery mutation occurred in
this review.

Verdict: **PASS**

## Checked against the request's own checklist

- **Hashes the immutable requested archive generation before promoting**: `main.py`'s `/promote`
  binds the source blob with `client.bucket(archive_bucket_name).blob(archive_object,
  generation=int(archive_generation))` — the generation is part of the blob reference itself, so
  `source.reload()` and the subsequent `sha256_for_blob(source)` both read that exact generation,
  not "whatever is current." If the requested generation no longer exists, the underlying client
  raises `NotFound` before any hash or copy is attempted (unhandled, so it fails as a 500 rather
  than a clean 4xx — a minor error-taxonomy gap, not a correctness or fail-open issue; see note
  below).
- **Create-only promotion**: `destination.rewrite(source, token=rewrite_token,
  if_generation_match=0)`, looped until the returned token is `None` (correct handling of GCS's
  chunked rewrite protocol — a single call is not guaranteed to finish for larger objects).
  `if_generation_match=0` is GCS's precondition for "destination must not already exist";
  `PreconditionFailed` is caught and returned as 409 "production destination already exists;
  create-only promotion refused." Correct create-only semantics.
- **Verifies destination size/CRC32C**: after the rewrite loop, `destination.reload()` then
  `destination.size != source.size or destination.crc32c != source.crc32c` raises before any
  success response is built. Correct.
- **Returns only exact evidence, never file contents**: response body is exactly `archive_uri`,
  `archive_generation`, `production_uri`, `production_generation`, `size_bytes`, `crc32c`,
  `sap_file_name`, `file_sha256` — traced every field to a value derived from the reloaded
  `source`/`destination` blob metadata or the validated request, nothing reads/returns object
  bytes back to the caller.
- **Name validation — explicit SAP-facing filename, not archive-name inference**: `_FILENAME =
  re.compile(r"^[A-Za-z0-9][A-Za-z0-9._-]*\.csv$")` validates `sap_file_name` from the request
  body; `production_object` is computed as `configured_name("PRODUCTION_PREFIX") + "/" +
  sap_file_name` and the request's own `production_object` field must equal that exact
  concatenation — the archive's own object name/basename is never read to construct the
  destination name anywhere in this file. This is the direct fix for the LogID 21183 lesson
  (referenced in the workflow's own comment) of inferring the production basename from the archive
  path.
- **Source-generation binding carried end-to-end**: workflow's `promote_and_hash_exact_generation`
  posts `archive_generation: ${source_generation}` (read from the same `find_archive` BigQuery
  row used throughout `promote_daily_archive`); `gate_promotion` then asserts
  `promoted_archive_generation != source_generation` fails closed — so the promoter's response
  can't silently report a different generation than what was actually requested.
- **Bucket/prefix confinement**: `archive_bucket_name != configured_name("ARCHIVE_BUCKET")` and the
  equivalent check for `production_bucket_name` both reject mismatches before any GCS call — the
  caller-supplied bucket names in the request body are checked against fixed env-configured values,
  not trusted directly. Combined with the prefix-concatenation check above, the service cannot be
  made to write outside `interface-file/RCB_MOTOR/` regardless of what the caller passes.
- **DDL 062's required filename/SHA-256 arguments are supplied, in the correct order**: read the
  full (not just diffed) `delivery_call_head`/`delivery_call_tail` construction — the concatenated
  statement is `CALL sp_mark_v3_exact_delivery('<run_id>','<export_run_id>','<archive_uri>',
  '<archive_generation>','<production_uri>','<production_generation>',<size_bytes>,'<crc32c>',
  '<sap_file_name>','<file_sha256>')`, which matches `sp_mark_v3_exact_delivery`'s parameter order
  exactly: `(p_pipeline_run_id, p_export_run_id, p_archive_uri, p_archive_generation,
  p_production_uri, p_production_generation, p_size_bytes, p_crc32c, p_sap_file_name,
  p_file_sha256)` (reviewed previously in `docs/reviews/2026-08-05-7d4866a-claude.md` /
  `...-70e5671-claude.md`). Correct — this was the missing piece those earlier reviews flagged as
  needed before the procedure could actually be called with real evidence.
- **Fails closed on a missing delivery contract**: `require_delivery_contract` — if
  `promotion_service_url == "" or sap_file_name == ""`, calls `fail_closed` with step
  `UNIT6_DELIVERY_CONTRACT` before `promote_exact_archive` is ever reached. Both args default to
  `""` via `default(map.get(args, ...), "")` when not supplied, so an omitted arg fails closed
  rather than proceeding with an empty/undefined value.
- **Checks the returned binding (`gate_promotion`)**: asserts, in one condition, that
  `promoted_archive_uri`, `promoted_archive_generation`, `production_uri`, and
  `promoted_sap_file_name` all equal what was requested, and that `dest_generation`, `dest_size`,
  `dest_crc`, and `file_sha256` are all non-empty/non-zero — any mismatch or blank field routes to
  `fail_closed` with step `UNIT6_EXACT_PROMOTION` before `output` (and therefore before
  `persist_delivery`) is reached. Correct — the workflow does not trust the promoter's response at
  face value, it re-verifies every field it's about to persist.
- **Delivery stays disabled**: `delivery_enabled: false` (line 55) is unchanged from before this
  commit and is never reassigned anywhere else in the file (`grep -n delivery_enabled` shows only
  the one assignment and the one `switch` condition reading it) — confirmed, not just claimed.
- **No deployment, procedure CALL, GCS write, scheduler, Gmail, BigQuery mutation, or SAP action

  not built or pushed by this commit; the workflow YAML is a source file, not deployed. I did not

## Observation (not a required note)

A `NotFound` on `source.reload()` (requested archive generation already gone, e.g. a lifecycle
deletion) is not caught alongside `PreconditionFailed`/`ValueError`, so it would surface as an
unhandled 500 rather than a clean 4xx. This is a fail-*closed* outcome either way (no promotion
happens, no evidence is returned), so it doesn't block this review, but it's worth a follow-up
polish before the separately-required production approval/deploy step.

The `promotion_service_url` used as the OIDC `audience` is itself a workflow execution argument
(`default(map.get(args, "promotion_service_url"), "")`), the same pattern already used for
`project`/`run_id`/`alert_topic` elsewhere in this file — i.e. it inherits the existing trust
boundary (workflow execution is already restricted to authorized internal callers) rather than
introducing a new one. Flagging only so it's visible if that trust boundary is ever revisited.
